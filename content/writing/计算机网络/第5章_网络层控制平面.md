## 5.1 路由问题与信息模型

路由控制将拓扑, 可达性和管理策略转换为转发规则. **路径(path)** 是从源到目的经过的节点或链路序列; 最优要相对于某个目标定义, 可以是代价最低, 满足策略或避开某些链路, 不一定是跳数最少.

将网络抽象为图 $G=(V,E)$, 链路 $x\to y$的代价记为 $c(x,y)$. 未直接连接时记为 $\infty$, 本节点到自身代价为0. 本章最短路算例使用固定非负代价, 路径代价为链路代价之和; 有向链路两个方向可取不同值.

| 信息模型                      | 每个节点掌握什么                       | 典型计算         |
| ----------------------------- | -------------------------------------- | ---------------- |
| 链路状态(Link State, LS)      | 网络拓扑及各链路代价                   | Dijkstra         |
| 距离向量(Distance Vector, DV) | 本地邻接代价, 邻居报告的到各目的的估计 | Bellman-Ford迭代 |

LS的全局信息不等于只有一个中心节点计算. 多台路由器都可获得同一拓扑, 各自以自己为源计算. DV则不要求每个节点重建全网拓扑.

静态路由(static routing)主要由人工或固定配置提供; 动态路由(dynamic routing)通过协议交换信息, 随拓扑和代价变化更新. 动态不表示每个分组都选择一条新路径.

## 5.2 链路状态与Dijkstra算法

各路由器发布本地链路状态, 经泛洪(flooding)传播, 使同一区域内节点形成尽量一致的拓扑数据库. 然后各自计算最短路径树(shortest-path tree).

设源为 $s$, $S$为已确定最短距离的节点集合, $D(v)$为到$v$的当前估计, $p(v)$为前驱.

1. 初始化 $S=\{s\}$, $D(s)=0$, 对其余节点令 $D(v)=c(s,v)$, 非邻居为无穷.
2. 从 $V-S$中选 $D(w)$最小的节点 $w$, 将其加入 $S$.
3. 对未确定的邻居 $v$松弛(relax):

$$
D(v)\leftarrow\min\bigl(D(v),D(w)+c(w,v)\bigr).
$$

4. 若经$w$改善距离, 设置 $p(v)=w$. 重复直到所有可达节点确定.

选择当前最小估计后即可确定其最短距离, 依赖非负链路代价. 相同最小值可以按约定任取; 最短路径可能不唯一, 不同合法选择可产生不同的树.

### 一次完整计算

设无向图的边为 `A-B:2, A-C:5, B-C:1, B-D:4, C-D:1, C-E:5, D-E:2`, 源为A. 下表只记录尚未确定节点的估计及其前驱.

| 加入的节点 | 已确定集合 | B     | C     | D     | E     |
| ---------- | ---------- | ----- | ----- | ----- | ----- |
| 初始化     | A          | 2,A   | 5,A   | 无穷  | 无穷  |
| B          | A,B        | 已定2 | 3,B   | 6,B   | 无穷  |
| C          | A,B,C      | 已定2 | 已定3 | 4,C   | 8,C   |
| D          | A,B,C,D    | 已定2 | 已定3 | 已定4 | 6,D   |
| E          | A,B,C,D,E  | 已定2 | 已定3 | 已定4 | 已定6 |

到E的前驱链为 `E<-D<-C<-B<-A`, 逆序得到路径 `A-B-C-D-E`, 代价6. A的转发表中, 到B, C, D, E的下一跳都是B. **前驱是目的附近的上一节点, 下一跳是源附近的下一节点**, 不能把$p(E)=D$直接当作A应发往D.

### 复杂度与振荡

朴素实现每次扫描全部未确定节点, 时间为 $O(|V|^2)$. 使用邻接表和堆可以达到 $O((|V|+|E|)\log|V|)$量级. 传播拓扑的报文开销与实际泛洪机制及边数有关, 不能把算法计算量当作网络消息数.

如果链路代价直接依赖当前负载, 大量流同时避开繁忙路径后, 新路径可能变得更忙, 于是又集体切回, 形成 **路由振荡(routing oscillation)**. 这种反馈不只影响LS, 也会影响其他使用快速变化度量的算法. 可通过平滑度量, 减缓更新, 避免全体同步等办法改善, 但具体稳定性要结合系统分析.

## 5.3 距离向量与Bellman-Ford

设 $D_x(y)$为节点$x$估计的到$y$的最小代价, 邻居集合为 $N(x)$. Bellman-Ford方程为

$$
D_x(y)=\min_{v\in N(x)}\left[c(x,v)+D_v(y)\right].
$$

到目的$y$的路径必须先走向某个邻居$v$. 选择使本地一步代价与邻居剩余距离之和最小的邻居, 就确定下一跳. 最小化对象是总和, 不是只看邻居宣告的距离.

### 异步更新过程

每个节点维护自己的距离向量, 以及最近收到的邻居向量:

1. 初始化到自身为0, 到直接邻居为链路代价, 其他为无穷.
2. 将本地向量发给邻居.
3. 收到邻居更新或发现本地链路变化后, 重新对受影响目的计算最小值.
4. 本地距离发生变化时再通知邻居.

算法可以分布式, 异步运行. 为方便手算, 可以额外假定所有节点同步交换, 每轮只使用上一轮的向量, 不能在同一轮内随意使用还未传播到当前节点的最新结果.

> **例.** 三角网络`X-Y:2, Y-Z:1, X-Z:7`. 初始X估计到Z为7. 收到Y报告的 $D_Y(Z)=1$后:
>
> $$
> D_X(Z)=\min(7,2+1)=3,
> $$
>
> 下一跳改为Y. 在同步轮次中, 第一轮后的估计包含至多经一次邻居更新发现的路径; 更远信息需要继续逐跳传播.

### 好消息与坏消息

链路代价下降时, 新的低代价可逐步向外传播. 代价上升或链路失效时, 邻居旧向量可能仍宣告一条实际依赖本节点的路径, 导致相互误信.

设原来`X-Y:1, Y-Z:1`, Z到X经Y, 估计2. X-Y失效后, 若Y先收到Z旧估计2, 会误以为经Z到X的代价为3. Z随后依据Y的新估计改成4, Y再改成5, 不断增大. 两者实际上在彼此之间形成路由环路.

这称 **计数到无穷(count-to-infinity)**. 原因是仅有距离值不能说明路径是否又经过自己, 不是Bellman-Ford最短路方程本身算错.

**毒性逆转(poisoned reverse)**: 若Z到X的下一跳为Y, Z向Y报告到X为无穷, 而不是2. 这样Y就不会依据这条依赖自己的路径绕回Z. 它能处理典型两节点互相依赖, 不能保证消除任意更长环路. 分割地平线(split horizon)则是不向某邻居重新通告经该邻居学到的路由.

### LS与DV比较

| 项目     | LS                                           | DV                             |
| -------- | -------------------------------------------- | ------------------------------ |
| 交换内容 | 本地邻接状态                                 | 到各目的的距离估计             |
| 传播对象 | 经泛洪到区域内节点                           | 直接邻居                       |
| 本地计算 | 基于拓扑计算整棵最短路径树                   | 基于邻居估计迭代               |
| 主要风险 | 拓扑数据库暂时不一致, 更新开销, 负载反馈振荡 | 收敛慢, 暂态环路, 计数到无穷   |
| 错误传播 | 错误链路状态可影响多台节点计算               | 错误距离可被邻居继续依赖并传播 |

稳定性, 安全性与实现机制都影响结果, 不能简单认定一种在所有场景下都优于另一种.

## 5.4 自治系统与OSPF

因特网规模很大, 不宜把所有路由器和链路都作为一个平面图运行同一套路由控制. **自治系统(Autonomous System, AS)** 由统一管理与路由策略下的一组网络组成.

- **域内路由(intra-AS / intradomain routing)** 处理一个管理域内部的可达性与路径.
- **域间路由(inter-AS / interdomain routing)** 处理不同AS之间的可达性与策略.
- **边界路由器(border / gateway router)** 连接本AS与其他AS.

域内可侧重性能与管理便利; 域间必须考虑商业关系, 对外出口与过境策略. 实际大型AS可通过重分发连接多种内部路由域, 因此AS不等于所有内部设备只能运行同一个协议.

### OSPF链路状态路由

**开放最短路径优先(Open Shortest Path First, OSPF)** 是域内链路状态协议. 路由器交换链路状态通告(Link-State Advertisement, LSA), 建立数据库并运行Dijkstra计算路径.

OSPF直接承载在IP上, 不使用TCP或UDP端口; OSPFv2使用IP协议号89. 链路代价由配置或相应规则决定, 不能将带宽数值直接当作代价相加. 认证机制需要相应配置和版本支持, 不能认为任何OSPF报文天然都经过安全认证.

### 分层OSPF

OSPF可划分区域(area), 以骨干区域Area 0连接各区域. 路由器对本区域保有更详细拓扑, 跨区域则通过区域边界提供的可达性信息转发, 从而限制拓扑传播与重新计算范围.

| 角色                                    | 作用                           |
| --------------------------------------- | ------------------------------ |
| 内部路由器(internal router)             | 接口位于同一区域               |
| 区域边界路由器(Area Border Router, ABR) | 连接区域与骨干, 提供跨区域信息 |
| 骨干路由器(backbone router)             | 在骨干区域中参与路由           |
| AS边界路由器(AS Boundary Router, ASBR)  | 引入来自其他路由域的外部信息   |

ABR和ASBR按不同职责命名, 不能因为都有边界就混为一谈. 分层降低状态规模, 但汇总后的信息较粗, 不一定保持全网平面图中最细粒度的最优选择.

## 5.5 BGP: 可达性, 路径与策略

**边界网关协议(Border Gateway Protocol, BGP)** 是因特网域间路由的主要协议. 它宣告目的前缀(prefix)及路径属性(path attributes), 选择策略允许的路由, 不是单纯计算全网物理链路最短路.

| 会话               | 对等体关系 | 目的                 |
| ------------------ | ---------- | -------------------- |
| eBGP(external BGP) | 不同AS之间 | 学习和发布跨AS可达性 |
| iBGP(internal BGP) | 同一AS内部 | 分发BGP路由信息      |

BGP对等体通过TCP会话交换消息, 通常使用端口179. iBGP不是OSPF的另一名称: iBGP分发外部路由, OSPF等内部协议提供到相关下一跳的内部可达性.

### 路由属性

| 属性       | 含义                                       |
| ---------- | ------------------------------------------ |
| AS-PATH    | 路由所经过的AS序列, 对外发布时通常加入本AS |
| NEXT-HOP   | 到该目的路由应进一步解析的下一跳地址       |
| LOCAL_PREF | AS内部表达的本地偏好, 用于策略选择         |

若收到的AS-PATH包含本AS编号, 通常拒绝该路径, 以避免AS级环路. 这与DV只报告距离不同, BGP是路径向量(path-vector)思想.

> **例.** AS3对外发布前缀P. AS2从AS3学到`AS3 -> P`, 再向AS1发布时形成`AS2 AS3 -> P`. AS1若通过别处收到包含AS1的路径, 不能再次选它绕回自己.

### 从BGP路由到具体输出端口

内部路由器先根据BGP选择到外部前缀的路由及NEXT-HOP, 再使用域内路由找到该下一跳的实际输出接口. 因而一个外部前缀的转发表项可能同时依赖BGP和OSPF, 不是必须在两者中二选一.

### 策略与出口选择

在用于理解的简化比较中, 先考虑本地策略偏好, 再比较AS-PATH等属性, 其后才可能比较到NEXT-HOP的域内代价. 完整BGP选择还包含其他属性和规则, 具体条件必须明确.

**热土豆路由(hot-potato routing)** 在此前候选条件相同的情况下, 选域内代价较低的出口, 尽快把流量交给外部网络. 它不等于不顾所有更高优先级属性, 永远选最近出口.

> **例.** P可从G1, G2离开AS. 若两条路由此前属性相同, 内部路由器到G1代价10, 到G2代价4, 可选G2. 若本地策略明确更偏好G1, 不能仅凭G2较近就直接改选G2.

路由发布本身也执行策略. 一个ISP通常愿意转运与自身客户有关的流量, 不一定愿意免费替两个非客户网络提供过境(transit). 一个双宿主(multihomed)客户若不愿成为两个上游之间的过境网络, 可限制向上游发布从另一上游学到的路由.

**学到一条路由, 选择这条路由, 再把它发布给别人, 是三个不同决策.** 接收策略和发布策略共同决定其他网络能看到哪些路径.

### BGP消息

| 消息         | 作用                           |
| ------------ | ------------------------------ |
| OPEN         | TCP连接建立后, 协商BGP会话参数 |
| UPDATE       | 发布新路由或撤销旧路由         |
| KEEPALIVE    | 确认/维持会话存活              |
| NOTIFICATION | 报告错误并关闭会话             |

OPEN不负责替代TCP三次握手, 也不能仅凭存在OPEN就认为对等体已获得密码学身份认证.

## 5.6 SDN控制器与OpenFlow

目的地址转发对某一目的通常采用同一组转发逻辑, 仅调整最短路权重不容易表达所有需求, 如按来源区分路径或协调多种访问控制. SDN把网络状态管理, 控制应用和底层转发分离, 提供可编程接口.

```text
路由 / 访问控制 / 负载均衡应用
             |
        北向接口
             |
    控制器与网络状态数据库
             |
        南向接口
             |
       转发设备与流表
```

**北向接口(northbound interface)** 给上层应用提供拓扑, 路径, 意图等抽象; **南向接口(southbound interface)** 与设备交换状态和规则. OpenFlow是南向机制的一种, 不是SDN全部.

控制器管理链路状态, 设备信息, 主机位置, 流表和统计. 物理上可由多个实例共同实现, 需要处理故障, 状态一致性和扩展能力. 不应把所有业务分组都送往控制器再逐个转发.

### OpenFlow交互

| 方向         | 消息类别                 | 含义                         |
| ------------ | ------------------------ | ---------------------------- |
| 控制器到设备 | features / configuration | 查询能力或设置配置           |
| 控制器到设备 | flow modification        | 增删改流表项                 |
| 控制器到设备 | packet-out               | 指示如何发送一个分组         |
| 设备到控制器 | packet-in                | 将某个分组及上下文报告控制器 |
| 设备到控制器 | port-status              | 通知端口变化                 |
| 设备到控制器 | flow-removed             | 通知流表项删除               |

链路故障的一个控制过程是: 设备报告端口变化 -> 控制器更新拓扑 -> 路由应用重新计算 -> 生成需要调整的规则 -> 下发相关设备. 规则更新期间仍需防止暂态环路或黑洞, 逻辑集中不会自动消除这些问题.

OpenDaylight和ONOS是控制器架构实例. 理解重点是网络状态层, 设备通信层与应用抽象层如何协作, 而非记住某个产品的模块名称.

## 5.7 ICMP, ping与traceroute

**因特网控制报文协议(Internet Control Message Protocol, ICMP)** 传递网络层差错和诊断信息. ICMP由IP承载, 不是TCP/UDP应用, 没有TCP/UDP端口号. IPv4的协议号为1.

消息包含Type, Code, Checksum及具体内容. 差错报文通常包含触发差错的原IP首部和部分负载, 便于发送端关联原始通信; 不保证只会包含固定且唯一长度的数据.

| IPv4 Type / Code | 意义               |
| ---------------- | ------------------ |
| 8 / 0            | Echo Request       |
| 0 / 0            | Echo Reply         |
| 3 / 0            | 目的网络不可达     |
| 3 / 1            | 目的主机不可达     |
| 3 / 3            | 目的端口不可达     |
| 3 / 4            | 需要分片但设置了DF |
| 11 / 0           | 转发时TTL耗尽      |

**ping** 通常发送Echo Request, 根据Echo Reply测量可达性与RTT. ping成功说明相应探测得到了回应, 不说明Web等应用一定正常. ping失败也不必然说明主机离线, 可能因ICMP过滤或限速.

### UDP traceroute的终止机制

1. 源端向目的主机的某个通常未使用的UDP端口发送探测, 从TTL=1开始.
2. 第$n$跳使TTL耗尽时, 丢弃探测并回送ICMP Time Exceeded.
3. 源端记录每个应答的来源及RTT, 逐渐增大TTL.
4. 探测最终到达目的主机, 该UDP端口没有接收进程时, 目的端返回ICMP Port Unreachable, 源端据此知道已到达.

也存在ICMP或TCP探测的traceroute, 它们的目的端终止应答不同. 沿途RTT是源到该节点再返回的测量, 不是相邻跳的单向耗时. DNS反向解析可以给应答地址补主机名, ICMP报文本身不必携带路由器名字.

## 5.8 网络管理: SNMP, NETCONF与YANG

路由决定怎样送数据, 网络管理还要解决设备配置, 故障告警, 计数统计与状态查询. **配置状态(configuration state)** 表示希望设备如何运行, **运行状态(operational state)** 表示设备实际情况, 两者不能混为一谈.

管理系统包含管理服务器(manager), 被管理设备(managed device), 设备上的代理(agent), 管理数据和协议.

### SNMP与MIB

**简单网络管理协议(Simple Network Management Protocol, SNMP)** 允许管理端读取或设置代理维护的对象, 也允许代理主动告警. **管理信息库(Management Information Base, MIB)** 描述被管理对象, 每个对象通过对象标识符(Object Identifier, OID)等定位.

| 操作           | 用途                   |
| -------------- | ---------------------- |
| GetRequest     | 读取指定对象           |
| GetNextRequest | 获取后续对象, 便于遍历 |
| GetBulkRequest | 批量读取               |
| SetRequest     | 修改可写对象           |
| Response       | 返回结果或错误         |
| Trap           | 代理主动通知事件       |

读取某接口累计发送字节数得到的是计数器, 不是瞬时带宽. 若两次采样间隔 $\Delta t$, 计数差为 $\Delta B$ byte, 则区间平均速率约为 $8\Delta B/\Delta t$ bit/s, 还需处理计数器回绕, 重启清零等情况.

### NETCONF配置流程

**网络配置协议(Network Configuration Protocol, NETCONF)** 使用安全可靠传输承载RPC与XML数据, 管理设备配置和查询状态. 常见流程为交换`hello`及能力列表 -> 多次`rpc` / `rpc-reply` -> 关闭会话.

| 操作              | 含义                                         |
| ----------------- | -------------------------------------------- |
| `get-config`      | 读取指定配置数据存储                         |
| `get`             | 读取配置及运行状态                           |
| `edit-config`     | 修改指定配置                                 |
| `lock` / `unlock` | 对配置存储加锁/解锁                          |
| `commit`          | 支持candidate能力时, 将候选配置提交到running |

候选配置, 回滚及确认提交等能力需由设备支持和协商. 这些机制有助于避免不完整配置, **不能仅因使用NETCONF就认为跨多台设备天然具有一个自动原子事务**. 多设备协调仍需控制器组织, 必要时处理失败与回滚. [NETCONF能力与操作](https://www.rfc-editor.org/rfc/rfc6241.html)

**YANG** 是管理数据的建模语言, 描述字段, 类型, 层次和约束; NETCONF是交换与操作这些数据的协议. YANG不是一种网络传输, 也不是仅仅把XML换个名字.
