## 3.1 运输层服务与复用

网络层提供 **主机到主机(host-to-host)** 的逻辑通信, 运输层提供 **进程到进程(process-to-process)** 的逻辑通信. 运输协议主要运行在端系统上, 利用IP服务, 通过端口, 检错及其他机制扩展其能力.

IP提供 **尽力而为(best-effort)** 交付, 不保证不丢失, 不损坏, 有序或准时. TCP在其上实现可靠字节流; UDP提供较简单的数据报服务. 二者均不保证固定时延或最低带宽.

**复用(multiplexing)**: 发送端接收多个socket的数据, 加入运输层首部, 交给网络层.

**分用/解复用(demultiplexing)**: 接收端根据首部信息, 把收到的数据交给相应socket.

### UDP分用

对于绑定到本地地址和端口, 未调用connect的普通UDP socket, 由 **目的IP地址, 目的端口** 确定接收socket. 不同来源的数据报只要发往同一个本地端点, 就可以交给同一socket. 来源地址由 `recvfrom`交给应用, 用于回复或区分客户.

### TCP分用

已建立TCP连接由四元组标识:

$$
(\text{源IP},\text{源端口},\text{目的IP},\text{目的端口}).
$$

一个服务器可在同一目的端口接受多个客户端连接, 因为源IP或源端口不同. 例:

```text
(A, 9157, B, 80)
(C, 5775, B, 80)
(C, 9157, B, 80)
```

三条连接均访问B的80端口, 但对应不同连接socket. 监听socket负责接受连接, 连接socket负责该连接的数据交换; 两者不应混为一谈.

## 3.2 UDP与因特网校验和

**用户数据报协议(User Datagram Protocol, UDP)** 无连接: 不在通信前握手, 每个数据报独立处理. 其首部较小, 不内置重传, 流量控制或拥塞控制.

优势是无需等待建连, 状态与处理开销小, 应用可自行决定发送方式. 代价是UDP本身不保证可靠, 有序交付. DNS, 简单网络管理协议(Simple Network Management Protocol, SNMP)以及QUIC等使用UDP; 所需的额外可靠性或拥塞控制可由上层实现.

### UDP首部

| 字段                       | 位数 | 含义                            |
| -------------------------- | ---- | ------------------------------- |
| 源端口(source port)        | 16   | 发送端的端口                    |
| 目的端口(destination port) | 16   | 接收端的端口                    |
| 长度(length)               | 16   | UDP首部与数据的总长度, 单位byte |
| 校验和(checksum)           | 16   | 检测传输中的比特错误            |

UDP首部共8 byte. 若长度字段为1008, 则UDP数据为1000 byte; 该长度不包含IP首部.

### 校验和的计算

发送端将数据划分为16-bit字, 使用 **反码加法(one's-complement addition)** 求和, 再逐位取反:

1. 将校验和字段置零, 组成待检验内容.
2. 按16-bit字相加; 最高位产生进位时, 将进位加回低16位, 称回卷进位(end-around carry).
3. 对最终16-bit和逐位取反, 写入校验和字段.

**补充**: UDP实际计算还覆盖IP地址等组成的伪首部(pseudo-header), 用来帮助发现错误投递; 奇数长度的数据需补零参与计算, 补零不是UDP实际负载.

> **例** 两个16-bit字为 `0xE666`与`0xD555`:
>
> ```text
> 普通和: 0xE666 + 0xD555 = 0x1BBBB
> 回卷:   0xBBBB + 1      = 0xBBBC
> 取反:  ~0xBBBC          = 0x4443  (仅保留16位)
> ```

接收端对包含校验和的内容同样求反码和, 正常应得到全1, 即 `0xFFFF`. 这与"先把校验和字段清零, 重新计算再比较"是等价检验思路.

**检错通过不保证绝对无错.** 不同位置的变化可能相互抵消, 例如一个字增加1, 另一个减少1, 和不变. 校验和也不提供抵抗恶意篡改的密码学认证能力, 更不能用它恢复丢失分组.

## 3.3 可靠数据传输: 从出错到丢失

**可靠数据传输(reliable data transfer, rdt)** 向上层提供完整, 按序, 无重复的数据交付, 底层却可能损坏或丢失分组. 发送方不能直接知道接收方状态, 必须通过反馈或超时判断.

可以用有限状态机(Finite State Machine, **FSM**)描述协议: 状态记录当前在等待什么; 事件触发检查, 发送, 交付或状态改变. 以下模型讨论单向数据传输, 但反馈在反方向传输.

四个接口: `rdt_send`接受上层数据, `udt_send`向不可靠信道发送, `rdt_rcv`处理到达分组, `deliver_data`将数据交付上层.

### rdt1.0: 理想信道

信道既不损坏也不丢失. 发送端直接构造并发送分组, 接收端直接提取并交付. 无需确认, 序号或重传.

### rdt2.0: 数据可能损坏

增加校验和与反馈:

- **肯定确认(acknowledgement, ACK)**: 正确收到.
- **否定确认(negative acknowledgement, NAK)**: 检测到错误, 请重传.

发送端发一个分组后等待反馈; 收到ACK才接受并发送下一份数据, 收到NAK则重传. 此为 **停止等待(stop-and-wait)**.

问题在于ACK/NAK也可能损坏. 此时发送端不知接收端是否已成功交付; 直接重传可能造成上层收到重复数据.

### rdt2.1: 序号区分重复

数据分组加入 **序号(sequence number)**, 接收端记录期望序号. 收到预期且正确的分组才交付并切换期望值; 收到重复分组则再次确认, 但不重复交付.

停止等待中一次只有一个待确认分组. 假设信道不把已完成一轮确认的旧分组留到之后的编号复用阶段, 用0, 1交替即可: 接收端只需区分当前的新分组和上一个分组的重传副本. 如果旧数据可能跨越多轮滞留并重排, 还需要额外的序号空间或报文寿命约束, 不能无条件只用1-bit序号.

发送端收到损坏反馈或NAK便重传. 序号解决的是重复交付问题, 没有自动解决丢包后永远等不到反馈的问题.

### rdt2.2: 只使用ACK

取消NAK. 接收端遇到损坏或非预期分组时, 重发 **上一个正确分组的ACK**, ACK明确带序号. 发送端看到对旧分组的ACK, 便知道当前分组尚未被正确确认, 采取重传.

这里ACK($n$)表示"分组$n$已收到"; 后文TCP的ACK($a$)表示"下一个期望字节为$a$", 二者编号语义不同.

### rdt3.0: 还可能丢包

如果数据或ACK丢失, 仅靠反馈会永久等待. rdt3.0增加 **计时器(timer)**: 发送数据后启动计时; 收到有效的当前ACK则停止计时并推进; 超时则重传当前分组并重启计时.

在这里的rdt3.0状态机中, 等待期间遇到损坏或非当前ACK先忽略, 靠超时恢复, 不是看到任意重复ACK都立即重传.

| 情况              | 发送端/接收端如何恢复                             |
| ----------------- | ------------------------------------------------- |
| 数据丢失          | 发送端超时重传, 接收端正常接收                    |
| ACK丢失           | 发送端超时重传; 接收端识别重复, 不再交付, 重新ACK |
| 数据损坏          | 接收端不交付; 发送端最终通过有效反馈或超时恢复    |
| ACK延迟, 提前超时 | 可能产生重复数据; 序号用于排除重复交付            |

**超时说明"尚未及时确认", 不证明数据一定丢失.** 可靠性必须容忍误判造成的重复传输.

| 信道问题       | 所需机制   | 机制解决的问题   |
| -------------- | ---------- | ---------------- |
| 比特错误       | 校验和     | 发现损坏         |
| 不知是否收到   | ACK/反馈   | 传递接收状态     |
| 错误或缺失数据 | 重传       | 再次尝试交付     |
| 重复传输       | 序号与去重 | 避免上层重复交付 |
| 无反馈         | 超时计时器 | 避免永久等待     |

## 3.4 停止等待性能与流水线

设数据分组 $L$ bit, 发送速率 $R$ bit/s, 往返传播等等待为 $RTT$; 忽略ACK发送时间和处理开销. 一个停止等待周期为 $L/R+RTT$, 发送方忙于发送的时间仅为 $L/R$, 因此

$$
U_{\mathrm{sender}}=\frac{L/R}{RTT+L/R},\qquad
T_{\mathrm{stop}}=UR=\frac{L}{RTT+L/R}.
$$

> **例题** $R=1$ Gbit/s, $L=8000$ bit, 单向传播15 ms, 即 $RTT=30$ ms:
>
> $$
> L/R=8\ \mu s=0.008\text{ ms},\qquad
> U=\frac{0.008}{30.008}\approx0.000267.
> $$
>
> 利用率约 $0.0267\%$, 吞吐量约 $267$ Kbit/s. 链路很快, 但发送端大部分时间都在等ACK.

**流水线(pipelining)** 允许多个未确认分组同时在途中(in flight), 使发送与等待重叠. 代价是需要更大的序号空间, 发送缓存, 以及更复杂的重传规则.

> **补充推导.** 若最多允许 $N$ 个未确认分组, 无丢包且接收端及时ACK, 则
>
> $$
> U\approx\min\left(1,\frac{NL/R}{RTT+L/R}\right).
> $$
>
> 要连续占满链路, 需要
>
> $$
> N\ge\left\lceil\frac{RTT+L/R}{L/R}\right\rceil
> =\left\lceil1+\frac{R\times RTT}{L}\right\rceil.
> $$

**带宽时延积(Bandwidth-Delay Product, BDP)** 是带宽与时延的乘积, 这里明确采用往返时间:

$$
BDP=R\times RTT.
$$

$R$是瓶颈链路的发送速率, 单位bit/s; $RTT$是从发送到反馈返回所需的往返时间, 单位s. 相乘后单位是bit, 表示等待一轮反馈期间链路能够发送的数据量, 不是速率.

> **例.** $R=100$ Mbit/s, $RTT=40$ ms $=0.04$ s, 则 $BDP=100\times10^6\times0.04=4\times10^6$ bit $=500000$ byte. 为避免发送后一直等ACK, 在途数据窗口需要达到约500 kB的量级.

如果计算的仅是单向链路中正在传播的比特数量, 应使用 $R\times d_{\mathrm{prop}}$. 前面的窗口利用率公式把分组传输时间与RTT分开计算, 所以精确占满条件多出一个分组的传输时间; 当 $L/R\ll RTT$时, 窗口量级主要由BDP决定.

## 3.5 回退N步GBN

**回退N步(Go-Back-N, GBN)** 使用发送窗口与 **累积确认(cumulative ACK)**. 以下采用经典接收策略: 丢弃乱序分组, 不缓存.

### 发送端状态

设窗口大小为 $N$, `base`为最早未确认分组, `nextseqnum`为下一个待发送序号.

```text
序号 < base                 已确认
[base, nextseqnum)          已发送, 未确认
[nextseqnum, base + N)      窗口内, 可发送
序号 >= base + N            当前不可发送
```

只有 `nextseqnum < base+N` 时才能发送新分组. 发送端保存未确认分组用于重传.

| 事件                     | 操作                                                             |
| ------------------------ | ---------------------------------------------------------------- |
| 上层提供数据, 窗口有空间 | 构造分组并发送, `nextseqnum++`; 若是第一个未确认分组则启动计时器 |
| 收到有效的新ACK($n$)     | 确认所有序号不大于$n$的分组, 令 `base=n+1`                       |
| 所有在途分组已确认       | 停止计时器                                                       |
| 仍有未确认分组           | 为最早未确认分组重启计时器                                       |
| 超时                     | 重传当前所有已发送但未确认的分组, 重启计时器                     |

"回退N步"不表示每次必定重传恰好N个, 而是重传 **当前未确认的整个在途区间**.

### 接收端状态

接收端记录 `expectedseqnum`: 正确收到该序号则交付, 发送ACK, 并推进期望值; 其他情况丢弃数据, 重新ACK最近连续正确接收的分组. ACK($n$)表示"到$n$为止已全部收到", 不是只确认$n$.

> **例.** 窗口 $N=4$, 发送0, 1, 2, 3, 分组2丢失: 接收端收0, 1并确认, 收3则丢弃并重发ACK1. 发送端若又发送4, 5, 它们也被丢弃. 分组2超时后, 发送端重传2, 3, 4, 5.
>
> 若ACK0丢失而ACK1收到, ACK1已涵盖0, 不需因此重传0. 累积确认能容忍部分ACK丢失, 但无法利用单个ACK准确表达"中间缺一块, 后面已有多块".

### 序号空间

若序号为 $k$ bit, 空间大小 $M=2^k$, 经典GBN接收窗口为1, 假设旧分组不会无限期滞留到任意后续轮次, 要求

$$
N\le M-1=2^k-1.
$$

若发送窗口覆盖全部 $M$ 个序号, 接收端收完一轮后又期望原起点; 一轮ACK全部丢失时, 旧分组重传会被误当成新一轮. 留出至少一个序号避免这种窗口重叠.

## 3.6 选择重传SR

**选择重传(Selective Repeat, SR)** 对分组单独确认, 单独超时重传. 接收端缓存窗口内的乱序分组, 最终仍按顺序向上交付.

### 发送端

发送窗口为 `[send_base, send_base+N-1]`. 发送端给各未确认分组维护逻辑计时器, 收到ACK($n$)便标记$n$已收到, 超时只重传对应分组.

**窗口移动由最早未确认分组决定.** 较后分组收到ACK, 不一定立即释放窗口右端空间; 只有窗口起点已确认, 才能跳过连续确认的分组推进起点.

### 接收端

设接收窗口为 `[rcv_base, rcv_base+N-1]`, 按循环序号理解:

| 到达情况                   | 处理                                         |
| -------------------------- | -------------------------------------------- |
| 正确分组在当前接收窗口内   | 发送该分组的ACK; 未到交付顺序则缓存          |
| 收到窗口起点分组           | 将它和其后已缓存的连续分组一起交付, 推进窗口 |
| 正确分组位于前一个窗口范围 | 再次ACK, 但不重复交付                        |
| 其他序号/损坏分组          | 不作为新数据接受                             |

为什么对旧分组重新ACK? 因为它可能已经交付, 但ACK丢失, 发送方仍在重传. 若接收方一律忽略这些旧分组, 发送方可能一直无法完成确认.

> **例.** 0, 1收到后交付, 2丢失, 3, 4, 5到达: 接收端缓存3, 4, 5, 并分别ACK; 发送端记录这些确认, 但起点停在2. 2超时后只重传2. 接收端收到2, 连续交付2, 3, 4, 5; ACK2到达后发送窗口可越过此前已确认的3, 4, 5.

### 为什么窗口不能超过序号空间的一半

设序号空间大小为 $M$, 双方窗口均为 $N$. 要求

$$
2N\le M,\qquad N\le2^{k-1}.
$$

> **反例.** 序号0, 1, 2, 3, $M=4$, 窗口 $N=3$. 接收端收完0, 1, 2后, 新窗口为3, 0, 1. 如果这些ACK全部丢失, 发送端重传旧0; 接收端看到0恰在新窗口内, 无法知道它是旧0还是下一轮的新0.

当 $M\ge2N$ 时, 在旧分组不会跨越多次完整编号循环的假设下, 最近旧窗口与当前新窗口不会重叠, 接收端能区分需要重新确认的旧分组与应该接受的新分组. 该限制针对 **编号回绕(wraparound)** 造成的歧义, 不能通过"记住最后一个ACK"简单解决.

### GBN与SR比较

| 项目                   | 经典GBN                        | SR                       |
| ---------------------- | ------------------------------ | ------------------------ |
| ACK语义                | 到$n$的累积确认                | 单独确认$n$              |
| 接收乱序分组           | 丢弃, 重新ACK连续前缀          | 窗口内缓存并ACK          |
| 计时器                 | 最早未确认分组的一个逻辑计时器 | 每个未确认分组各自计时   |
| 超时重传               | 当前未确认的在途区间           | 仅对应分组               |
| 发送缓存               | 保存未确认分组                 | 保存未确认分组及确认状态 |
| 接收缓存               | 无需缓存乱序数据               | 需要缓存乱序数据         |
| 等长双方窗口的序号要求 | $N\le2^k-1$, 接收窗口为1       | $N\le2^{k-1}$            |

GBN实现简单, 但单个丢包可能造成大量重传; SR减少重复传输, 但需要更多接收状态与缓存.

## 3.7 TCP字节流, 首部与确认

**传输控制协议(Transmission Control Protocol, TCP)** 是面向连接, 点对点, 全双工(full-duplex)的可靠有序字节流协议. 两个方向可同时传输, 分别维护各自的序号与确认进度; 一个方向的ACK可以捎带(piggyback)在反方向的数据报文段中.

TCP不保留应用消息边界. 发送两次100 byte, 不保证接收端调用两次就各得到100 byte. TCP承诺字节序列的交付, 应用协议负责消息划分.

### TCP首部与MSS

| 字段                           | 含义                                       |
| ------------------------------ | ------------------------------------------ |
| 源/目的端口                    | 16-bit, 各自标识通信端点                   |
| 序号(sequence number)          | 32-bit, 通常表示该段第一个数据字节的编号   |
| 确认号(acknowledgement number) | 32-bit, 下一个期望收到的字节编号           |
| 数据偏移/首部长度(data offset) | 4-bit, 以32-bit字即4 byte为单位            |
| 接收窗口(receive window)       | 接收端通告的接收能力, 用于流量控制         |
| 校验和                         | 检测首部和数据等内容的传输错误             |
| ACK                            | 确认号字段有效                             |
| SYN                            | 建立连接, 同步初始序号                     |
| FIN                            | 结束本方向的发送                           |
| RST                            | 重置连接                                   |
| PSH                            | 提示尽快向接收应用交付数据; 不构成消息边界 |
| URG, 紧急指针(urgent pointer)  | URG说明紧急指针有效, 用于紧急数据机制      |
| ECE, CWR                       | 与显式拥塞通知有关                         |
| 选项(options)                  | MSS, 窗口扩大, 时间戳, SACK等扩展信息      |

**首部长度**: 数据偏移字段以4 byte为单位. 无选项时TCP首部20 byte, 字段值为 $20/4=5$; 字段上限15, 对应60 byte首部. 区分字段值与实际字节数, 才能正确确定数据从哪里开始.

**最大报文段大小(Maximum Segment Size, MSS)** 是一个TCP段的数据负载上限, 不包括TCP/IP首部. 链路的 **最大传输单元(Maximum Transmission Unit, MTU)** 通常限制整个IP分组大小. 以MTU=1500 byte, IPv4首部20 byte, TCP首部20 byte为例, MSS=1460 byte; 不是所有路径都固定为1460.

### 字节序号与累积ACK

若 `Seq=1000`, 负载长500 byte, 则包含字节1000至1499, 接收端完整连续收到后返回 `ACK=1500`.

TCP的 `ACK=a`表示"$a$之前的字节已经连续收到, 下一个希望收到$a$", 不是"分组$a$已收到". 若字节1500至1999缺失, 而2000至2499先到, 接收端仍返回ACK1500, 不能确认到2500.

**SYN与FIN各消耗一个序号**; 无数据的纯ACK不消耗新的序号. 两个方向的初始序号独立. 例如一次字符回显:

```text
A → B: Seq=42, ACK=79, 数据'C'(1 byte)
B → A: Seq=79, ACK=43, 回显'C'(1 byte)
A → B: Seq=43, ACK=80, 无数据
```

B的ACK43确认A的字符, A的ACK80确认B的字符; 不能把两个方向的编号当成同一条序列.

## 3.8 TCP可靠传输与超时

### RTT估计

**样本RTT(SampleRTT)** 测量发送数据段至收到相应确认的时间. 在不使用时间戳消除重传歧义时, 不使用重传段的样本, 因为ACK可能对应第一次发送, 也可能对应重传, 存在歧义.

采用 **指数加权移动平均(Exponentially Weighted Moving Average, EWMA)** :

$$
EstimatedRTT\leftarrow(1-\alpha)EstimatedRTT+\alpha SampleRTT,
\qquad\alpha=0.125.
$$

新样本影响较大, 旧样本权重随时间指数衰减, 平滑偶然波动. 偏差估计为

$$
DevRTT\leftarrow(1-\beta)DevRTT+
\beta|SampleRTT-EstimatedRTT|,\qquad\beta=0.25.
$$

先忽略时钟粒度, 最小超时下限和重传退避, 用下式估计 **重传超时(Retransmission Timeout, RTO)**

$$
TimeoutInterval=EstimatedRTT+4DevRTT.
$$

RTT波动越大, 安全余量越大. 超时过短会误重传, 过长则丢包恢复慢.

**更新顺序与实际RTO**: 先用旧的平滑RTT更新偏差, 再更新平滑RTT. 完整RTO算法还考虑时钟粒度, 最小超时和超时后的指数退避. 下例只计算估计值, 不施加这些额外限制.

> **例.** 旧 $EstimatedRTT=100$ ms, 旧 $DevRTT=10$ ms, 新样本120 ms:
>
> $$
> DevRTT'=0.75\times10+0.25\times20=12.5\text{ ms},
> $$
>
> $$
> EstimatedRTT'=0.875\times100+0.125\times120=102.5\text{ ms}.
> $$
>
> 只使用上述估计表达式, 得到 $RTO'=152.5$ ms; 这不是已包含实际最小超时限制的结果.

### 简化发送端

| 事件                 | 操作                                             |
| -------------------- | ------------------------------------------------ |
| 上层有数据, 窗口允许 | 构造TCP段; 若计时器未运行则启动                  |
| 收到推进确认的新ACK  | 更新最早未确认字节; 有剩余未确认数据则重启计时器 |
| 超时                 | 重传最早未确认段, 重启计时器; 实际算法还会退避   |
| 收到3个重复ACK       | 快速重传最早未确认段                             |

TCP超时不按经典GBN规则重传整个窗口. TCP使用累积确认, 实际又可缓存乱序段, 使用选择性确认(Selective Acknowledgement, SACK); 不能把TCP直接等同于纯GBN或纯SR.

### 接收端ACK生成

ACK生成策略直接影响反馈时机和丢包恢复, 具有实际协议意义. 采用延迟确认时, 以下是经典TCP的规则:

- 顺序段到达且此前没有待发ACK: 可以暂缓确认, 等待后续段, 以减少独立ACK的数量.
- 又到达一个满尺寸的顺序段: 通常立即发送累积ACK, 一次确认两段.
- 超出期望序号的乱序段到达: 应立即发送重复ACK, 指出缺口起点, 加快丢失推断.
- 填补全部或部分缺口的段到达: 应立即反馈新的连续接收边界.

延迟ACK不能无限等待: 经典规范要求首个未确认段到达后500 ms内发出ACK, 并建议至少每两个满尺寸段确认一次. 500 ms是上限, 不是固定等待时间. 是否延迟, 等待多久都可能随实现而变化.

**做题时**: 题目明确给出每段确认或延迟确认策略时, 使用题设. 只分析确认号时, 按连续接收边界计算; 分析ACK数量, 时间线或拥塞窗口增长时, 必须另行说明ACK策略, 不能在未声明的情况下混用. 3.12节的逐轮窗口计算明确假定每段单独确认.

ACK说明运输层接收进度, 不说明应用已经读完或处理完数据.

### 丢ACK与快速重传

**累积确认覆盖丢ACK.** 发送段 `[92,100)` 与 `[100,120)`, ACK100丢失, 但ACK120到达: 两段都被确认, 不需仅为ACK100丢失而重传.

**快速重传(fast retransmit)** : 发送端已收到ACK100, 此后又连续收到3个ACK100, 说明后续数据很可能到达而100起的数据存在缺口, 于是不等超时, 重传缺失段.

三个重复ACK是 **最初的ACK之外的三次重复**. 重复ACK也可能由重排引起, 因此快速重传是一种丢失推断, 不是绝对证明; 窗口小, 后续分组不足时, 可能仍需靠超时发现丢失.

## 3.9 TCP流量控制

**流量控制(flow control)** 防止发送端压垮接收端: 数据进入TCP接收缓冲区的速度可能大于应用读取速度.

在简化的顺序接收模型中, 设接收缓冲容量为 $RcvBuffer$, 最后收到, 最后被应用读取的字节编号为 $LastByteRcvd,LastByteRead$, 接收窗口为

$$
rwnd=RcvBuffer-(LastByteRcvd-LastByteRead).
$$

接收端把可用空间通过TCP首部中的窗口字段通告给发送端. 发送端约束未确认数据量:

$$
LastByteSent-LastByteAcked\le rwnd.
$$

> **例.** 缓冲容量10000 byte, 尚未读出的数据6000 byte, 则通告窗口4000 byte. 若发送端已有1000 byte未确认, 在该简化状态下还能增加最多3000 byte的在途数据.

**补充: 零窗口.** 接收窗口变为0时, 发送端暂停正常新数据发送; 后续应用读走数据, 窗口可再次打开. 为防止窗口更新丢失导致永久等待, TCP使用零窗口探测(zero-window probing).

`rwnd`取决于接收端缓存; 拥塞窗口`cwnd`取决于发送端对网络拥塞的判断. 二者共同限制发送, 正常新数据的有效窗口近似为

$$
W_{\mathrm{effective}}=\min(rwnd,cwnd).
$$

## 3.10 TCP连接建立与关闭

### 三次握手

建立连接前, 需要确认双方愿意通信并同步状态, 例如两个方向的初始序号(Initial Sequence Number, ISN). 正常过程如下:

| 步骤 | 报文                                      | 客户端状态    | 服务器状态                      |
| ---- | ----------------------------------------- | ------------- | ------------------------------- |
| 1    | 客户端发送 `SYN=1, Seq=x`                 | `SYN-SENT`    | 等待接收/处理SYN                |
| 2    | 服务器发送 `SYN=1, ACK=1, Seq=y, Ack=x+1` | 等待SYN+ACK   | `SYN-RECEIVED`                  |
| 3    | 客户端发送 `ACK=1, Seq=x+1, Ack=y+1`      | `ESTABLISHED` | 收到有效ACK后进入 `ESTABLISHED` |

第三个段可以携带数据. SYN占一个序号, 因此确认分别为$x+1$和$y+1$.

**为什么两次不够?** 延迟到达的旧连接请求可能使服务器误以为客户正在请求新连接. 如果服务器仅发送答复就进入已建立状态, 会出现无人对应的半开连接, 甚至接受旧数据. 第三次握手要求客户端确认服务器这次选出的初始序号, 使服务器获得客户仍在参与本次连接的证据.

不能把理由缩成"双方各确认一次"而忽略延迟, 重传和旧连接状态; 也不能宣称三次握手解决了任意信道中的所有一致性问题.

### 关闭: 两个方向分别结束

TCP为全双工, 每个方向独立终止. 发送FIN意味着"我没有更多字节发送", 不意味着对端也已结束发送. 接收FIN后可继续发送剩余数据, 形成 **半关闭(half-close)**.

通常由A主动关闭:

| 步骤 | 消息/动作         | A状态                   | B状态                            |
| ---- | ----------------- | ----------------------- | -------------------------------- |
| 1    | A发FIN, 序号$x$   | `FIN-WAIT-1`            | 收到后确认并进入 `CLOSE-WAIT`    |
| 2    | B发ACK, 确认$x+1$ | 收到后 `FIN-WAIT-2`     | 可继续发送数据, 等待本地应用关闭 |
| 3    | B发FIN, 序号$y$   | 收到后准备确认          | `LAST-ACK`                       |
| 4    | A发ACK, 确认$y+1$ | `TIME-WAIT`, 等待后关闭 | 收到ACK后 `CLOSED`               |

ACK与FIN可以合并, 双方也可能同时关闭, 因此"四次挥手"描述典型过程, 不能理解为关闭一定有四个独立报文段.

### TIME-WAIT与2MSL

**最大报文段生存时间(Maximum Segment Lifetime, MSL)** 限制旧段在网络中存活的时间. 在正常主动关闭路径中, 发送最后ACK的一方进入TIME-WAIT, 等待2MSL:

- 若最后ACK丢失, 对端可重发FIN; 等待的一方仍能再次确认.
- 让旧连接的残留段有时间消失, 降低其干扰后续连接的风险.

TIME-WAIT不是"服务器等待应用关闭"; 那通常对应CLOSE-WAIT. MSL的具体取值依实现/设定而异, 不记成统一固定秒数.

## 3.11 拥塞的原因, 代价与反馈

**拥塞(congestion)** 是网络中的资源承受不了通信需求: 链路发送能力, 缓存等不足, 导致队列增长, 时延增加和丢包.

| 对比     | 流量控制             | 拥塞控制(congestion control) |
| -------- | -------------------- | ---------------------------- |
| 保护对象 | 接收端缓存与处理能力 | 路径中的网络资源             |
| 依据     | 接收端通告窗口       | 丢包, 时延或显式拥塞反馈     |
| 关键变量 | `rwnd`               | `cwnd`等                     |

按缓冲与路径条件, 拥塞代价可以分为三个层次:

1. **无限缓冲, 无丢包**: 负载逼近容量时队列与等待增大; 每条流的输出仍受共享容量限制.
2. **有限缓冲, 需要重传**: 总发送量包含原始数据与重传. 为交付相同有效数据, 需要更多链路容量; 过早超时产生不必要副本, 进一步降低goodput.
3. **多跳传输**: 一个分组若在后面的路由器丢失, 前面链路已为它消耗的容量和缓存也被浪费. 过度重传可造成更多拥塞, 甚至导致有效吞吐量下降.

因此"发得越快就收到得越快"只在未遇到资源限制时可能成立. 瓶颈已经持续忙碌时, 增加在途数据常只增加排队.

### 两类反馈

- **端到端拥塞控制(end-to-end congestion control)**: 网络不显式提供拥塞信息, 端系统从丢失, RTT等推断拥塞.
- **网络辅助拥塞控制(network-assisted congestion control)**: 路由器标记拥塞或提供速率信息, 端系统据此调整.

**显式拥塞通知(Explicit Congestion Notification, ECN)** 是后一类: 路由器可在IP首部标记拥塞, 接收端通过TCP反馈通知发送端. 其目标之一是在不必丢包的情况下传递拥塞信号, 涉及IP与TCP两层.

## 3.12 经典TCP拥塞控制: 慢启动, 避免与恢复

以下分析经典TCP Reno, 将算法规则与便于计算的条件分开. 窗口以byte计, MSS表示一个满尺寸段的数据字节数. 逐RTT计算时假定:

- 发送端持续有数据, 接收窗口不限制发送.
- 发送的段均为满尺寸, 每个新数据段产生一个ACK, ACK不丢失.
- RTT近似不变, 初始 $cwnd=1MSS$.
- 每轮能发送完整窗口, 因而丢失前的在途数据量FlightSize近似等于cwnd.
- 每轮内只考虑一次导致恢复的丢失事件.

这些条件使窗口轨迹可以手算, 并不是Reno协议对所有连接的固定配置. 延迟ACK, 窗口未用满或同一窗口多处丢失时, 需要按实际反馈重新分析.

**拥塞窗口(congestion window, cwnd)** 限制未确认的在途数据. 发送端不是每个RTT必须整批停下来等; "每RTT发送约一个窗口"是连续ACK驱动流水线的速率估计:

$$
T\approx\frac{cwnd}{RTT}\quad\text{byte/s}.
$$

### 慢启动(slow start)

在上述初始窗口设定下, 每个确认新数据的ACK使

$$
cwnd\leftarrow cwnd+MSS.
$$

若一轮内每段都被单独确认, 窗口约每RTT翻倍: $1,2,4,8,\ldots$ MSS. 名称中的"慢"指从较小窗口开始, 增长本身是指数级.

慢启动阈值(slow-start threshold, **ssthresh**)决定何时转为拥塞避免. 以下轨迹统一约定 $cwnd<ssthresh$ 时慢启动, 达到或超过阈值后采用拥塞避免. 初始窗口和阈值由条件给定, 不把1MSS视为所有实际连接的固定初始值.

### 拥塞避免(congestion avoidance)

采用 **加性增, 乘性减(Additive Increase, Multiplicative Decrease, AIMD)**:

- 加性增: 每RTT约增加1MSS.
- 乘性减: 出现拥塞反馈时, 降低窗口, 例如Reno重复ACK路径上的减半.

以byte计, 每个新ACK近似增加

$$
cwnd\leftarrow cwnd+\frac{MSS^2}{cwnd}.
$$

一个RTT约有 $cwnd/MSS$ 个ACK, 总增量约1MSS. 若以"段数"为窗口单位, 才写作每ACK增加 $1/cwnd$; 不能把两种单位混用.

### 超时与三次重复ACK的不同处理

**超时(timeout)** 被视为较严重的丢失信号. 在窗口被充分使用且未触及2MSS下限的条件下, 将 $ssthresh$ 近似设为丢失前窗口的一半, 令 $cwnd=1MSS$, 重传并重新慢启动.

**三次重复ACK(triple duplicate ACK)** 说明网络仍在交付一些后续段. Reno快速重传缺失段, 并进入 **快速恢复(fast recovery)**, 而不是把窗口立即降为1MSS.

| 事件                              | 上述满窗口假设下的动作                            |
| --------------------------------- | ------------------------------------------------- |
| 收到第3个重复ACK                  | $ssthresh=cwnd/2$; $cwnd=ssthresh+3MSS$; 快速重传 |
| 快速恢复中每多一个重复ACK         | $cwnd\leftarrow cwnd+MSS$, 允许时发送新段         |
| 收到确认新数据, 结束本次恢复的ACK | $cwnd=ssthresh$, 进入拥塞避免                     |
| 发生超时                          | $ssthresh=cwnd/2$, $cwnd=1MSS$, 重新慢启动        |

这里的 $+3MSS$ 是对已离开网络的3个段进行窗口"膨胀", 不是永久多得3MSS带宽. **快速重传是何时重发, 快速恢复是重发期间怎样管理窗口.** Tahoe也有快速重传, 但没有Reno式快速恢复, 三次重复ACK后回到慢启动.

**阈值的依据**: FlightSize是已经发送但尚未被累积确认的字节数. 经典减小阈值的基准为 $\max(FlightSize/2, 2MSS)$. 只有窗口基本用满时, 才能以 $cwnd/2$近似FlightSize的一半. 本节表格和例题采用该近似, 避免把未使用的窗口空间误算成在途数据.

### 窗口轨迹例题(补充)

设初始 $cwnd=1MSS$, $ssthresh=8MSS$, 按每RTT观察:

```text
无丢失: 1 → 2 → 4 → 8 → 9 → 10 → 11 → 12 MSS
                       达阈值后改为线性增长
```

窗口12MSS时出现3个重复ACK: 阈值变6MSS, 快速恢复暂为9MSS; 恢复ACK到达后回到6MSS, 再线性增长. 若窗口12MSS时发生超时: 阈值变6MSS, 窗口回到1MSS, 再慢启动至阈值附近. 画图时要分清"进入恢复时的暂时窗口"与"恢复结束后的窗口".

## 3.13 TCP吞吐量, 长肥网络与公平性

### 锯齿窗口的平均吞吐量

忽略慢启动, 超时和接收窗口限制; 假设持续有数据, RTT固定, Reno窗口从 $W/2$线性增长到$W$, 丢失后减半. 若 $W$以byte计, 则

$$
\bar W=\frac{W/2+W}{2}=\frac{3W}{4},\qquad
\bar T\approx\frac{3W}{4RTT}\quad\text{byte/s}.
$$

这个公式描述理想拥塞避免周期, 不是任意TCP连接的平均速度.

### 与丢失率的关系

现令 $W$以 **段数** 计, $p$为每发送一个段发生丢失的概率. 忽略离散边界, 在一个锯齿周期中, 约有 $W/2$轮, 每轮平均发送 $3W/4$段, 因而

$$
\frac{1}{p}\approx\frac{W}{2}\cdot\frac{3W}{4}
=\frac{3W^2}{8}.
$$

由此

$$
W\approx\sqrt{\frac{8}{3p}},\qquad
\bar T\approx\frac{3W\,MSS}{4RTT}
\approx\frac{1.22\,MSS}{RTT\sqrt p}.
$$

若MSS以byte计, 结果为byte/s; 换算bit/s需乘8. $p$表示段丢失率, 与分组长度不同. 该近似要求低丢失, RTT近似固定且大部分时间处于Reno拥塞避免; 高丢失, 频繁超时或其他算法不能直接套用.

### 长肥网络

**长肥网络(Long Fat Network, LFN)** 具有较大带宽时延积: 速率高, RTT长, 需要大量数据同时在途才能利用链路. 所需在途窗口约为 $R\times RTT$.

> **例.** $R=10$ Gbit/s, $RTT=0.1$ s, 需要约 $10^9$ bit, 即125 MB在途数据; 按每段1500 byte约为83333段. 若严格把1500当作含首部的IP分组大小, 应按实际MSS重新计算.

对上述经典Reno模型, 达到该速度所需丢失率约为 $2\times10^{-10}$, 说明单纯线性增长和丢失减半在高BDP环境下受限; 不是声称所有现代TCP都必须满足这么低的丢失率.

### 公平性

若 $K$条TCP连接共享容量 $R$的瓶颈, 理想目标是每条获得 $R/K$. AIMD在相同RTT, 固定连接数, 只处于拥塞避免等条件下能趋向公平分配.

两个连接以相同增量增加, 速率差不变; 同时按相同比例减少, 速率差缩小. 反复进行后分配趋近相等. 实际不同RTT, 算法和丢失情况会破坏这些理想假设.

**连接公平不等于用户公平.** 若已有9条连接, 某应用增加1条, 理想份额为 $R/10$; 若增加11条, 总连接数20, 该应用可合计获得 $11R/20$, 接近一半. UDP本身也不强制执行TCP式拥塞控制, 公平性不能仅靠协议名称保证.

## 3.14 CUBIC, 时延反馈与QUIC

### CUBIC: 围绕上次拥塞点探测

TCP CUBIC记录上次丢失时的窗口 $W_{\max}$. 窗口下降后, 先较快地接近原来的 $W_{\max}$, 接近时放慢增长, 谨慎探测; 越过该位置后再加速探测新的可用容量.

令 $K$表示减小窗口后, 三次增长曲线重新到达旧窗口 $W_{\max}$的时间. 窗口变化由距该时间点的距离的三次函数控制: 远离旧拥塞点时增长较快, 靠近时增长较慢. 这一时间驱动的探测方式区别于Reno每RTT增加约1MSS的线性增长; CUBIC的减小比例也不必与Reno相同.

### 基于时延和模型的控制

当瓶颈已持续忙碌, 增加发送量不提高交付速率, 却使队列增长, RTT增加. 因此可尝试在丢包前识别拥塞.

TCP Vegas比较:

$$
T_{\mathrm{expected}}\approx\frac{cwnd}{RTT_{\min}},\qquad
T_{\mathrm{actual}}\approx\frac{\text{测量区间交付字节数}}{\text{区间时长}}.
$$

$RTT_{\min}$近似无排队时的基准RTT. 实际吞吐明显小于期望值, 可能说明数据在排队, 于是降低窗口; 接近时可继续增加. 具体还需要阈值和稳定性处理, 不能只用一次RTT波动判定.

**瓶颈带宽与往返传播时间(Bottleneck Bandwidth and Round-trip propagation time, BBR)**. 理解上将其视为根据瓶颈带宽, 传播RTT估计建立路径模型的控制方法, 不能直接等同于Vegas的简单时延差规则.

### QUIC: UDP上的可靠多流运输

**QUIC** 是基于UDP的安全, 多路复用运输协议. 它在UDP承载之上实现可靠流和连接管理, 不依赖TCP提供可靠性.

QUIC把可靠传输状态与安全握手结合. 对没有额外重试的新连接, 客户端通常经过约1RTT即可建立相应状态并开始受保护的数据交换. 相比TCP建连后再进行TLS握手的串行过程, 它能减少建立开销; 丢包, 重试等条件仍会增加等待时间.

一个QUIC连接可承载多个流:

- 每个流独立维护字节顺序; 一个流缺数据, 不强制其他流等它补齐.
- 流之间仍共享连接资源与拥塞控制.
- UDP只是承载, QUIC自身提供ACK, 丢失恢复, 流量控制等能力.
- HTTP/3在QUIC上表达HTTP语义, 不是直接用UDP随意发送HTTP/1.1文本.

QUIC提供运输服务, 同时可作为用户态软件运行在UDP之上. 协议功能与软件实现位置是两个维度, 不能因为它由应用程序中的库实现, 就将其可靠传输功能视为普通业务逻辑.
