## 2.1 网络应用的通信模型

浏览器请求网页时, 本机的浏览器进程与远端的服务器进程交换报文. 网络应用就是由这样一些运行在不同端系统上的 **进程(process)** 组成的. 新增一种应用, 通常只需在端系统上部署程序, 不必改造沿途的核心路由器.

### 客户端-服务器与P2P

| 项目       | 客户端-服务器(client-server, C/S) | 对等体系结构(peer-to-peer, P2P)        |
| ---------- | --------------------------------- | -------------------------------------- |
| 服务提供者 | 可持续访问的服务器或服务器集群    | 对等方互相提供服务                     |
| 通信关系   | 客户端向服务器发起请求            | 对等方直接交换数据                     |
| 扩展方式   | 增加服务器, 带宽等资源            | 新对等方同时带来需求与上传能力         |
| 管理难点   | 服务器负载, 成本与可用性          | 节点加入离开, 地址变化, 资源与激励管理 |
| 例子       | Web, 邮件访问                     | BitTorrent文件分发                     |

主动发起这次通信的是 **客户端进程(client process)**, 等待联系的是 **服务器进程(server process)**. 这是通信中的角色, 不一定对应固定的设备类型. P2P 节点可以同时承担两种角色, 也可以借助中心服务器完成部分工作.

### 套接字与进程寻址

**套接字(socket)** 是应用进程使用运输层服务的接口. 应用决定发送什么, 操作系统和运输协议负责具体传输.

知道 IP 地址后, 还得知道把数据交给哪个应用. **端口号(port number)** 用来区分主机上的通信端点. 此外还要区分 TCP, UDP 等运输协议; TCP 连接怎样完整标识, 第 3 章会继续说明.

典型默认服务端口: HTTP使用TCP 80, HTTPS使用443, 服务器间SMTP传送邮件使用TCP 25, 传统DNS使用UDP或TCP 53. 这些是默认约定, 服务也可以配置到其他端口.

### 应用对运输服务的要求

| 要求                | 含义                     | 例子                   |
| ------------------- | ------------------------ | ---------------------- |
| 可靠性(reliability) | 数据不能缺失或错误交付   | 文件, 邮件, 交易       |
| 吞吐量(throughput)  | 需要足够的数据交付速率   | 视频播放需支撑选定码率 |
| 时延(timing)        | 数据需要及时到达         | 交互游戏, 实时通话     |
| 安全(security)      | 机密性, 完整性, 身份认证 | 登录, 支付等           |

**弹性应用(elastic application)** 可以适应获得的吞吐量, 例如文件传输; 带宽敏感应用若长期得不到必要速率, 则需降级或无法正常工作.

TCP提供可靠, 有序的字节流, 流量控制, 拥塞控制和连接建立, 但不保证固定时延, 最低吞吐量或加密. UDP提供数据报交付, 不内置可靠传输, 流量控制或拥塞控制. 应用也可以在UDP上自行实现可靠传输等能力, QUIC就是例子.

**运输层安全(Transport Layer Security, TLS)** 提供加密, 完整性与端点认证等能力. 常见部署是应用通过TLS库使用TCP; TCP本身不因此成为加密协议.

### 应用层协议包含什么

应用层协议规定消息类型, 语法(syntax), 语义(semantics)和交互规则. 应用, 应用层协议, 运输协议是三个不同概念: 浏览器是应用, HTTP是应用层协议, TCP或QUIC提供底层运输能力.

## 2.2 Web与HTTP

**万维网(World Wide Web, WWW)** 是因特网上的一类应用系统. 网页通常包含基础HTML文件以及图片, 脚本, 样式等对象(object), 对象可以来自不同服务器.

**超文本传输协议(Hypertext Transfer Protocol, HTTP)** 定义客户端获取, 提交或操作资源的请求与响应.**统一资源定位符(Uniform Resource Locator, URL)** 标识访问资源的位置, 例如:

```text
http://www.example.com:80/course/index.html
协议   主机名          端口 路径
```

一次网页访问可能需要DNS解析, 连接建立, 请求基础HTML, 解析引用, 再请求多个对象.**一个网页不是一个分组, 也不一定只对应一次HTTP请求.**

### 非持续连接与持续连接

**非持续HTTP(non-persistent HTTP)** 在一个TCP连接上至多传输一个对象, 之后关闭连接. 若网页有基础HTML和10张图片, 则需要11次对象传输, 11条TCP连接.

**持续HTTP(persistent HTTP)** 复用已经建立的连接来传输多个对象, 减少重复握手和系统开销. HTTP/1.1默认采用持续连接.

设一个小报文往返时间为 $RTT$, 对象传输时间为 $t_{\mathrm{obj}}$, 忽略DNS, TLS, 服务器处理, 请求报文传输与TCP启动影响, 则非持续HTTP获取单个对象的时间为

$$
T\approx 2RTT+t_{\mathrm{obj}}.
$$

第一个RTT用于建立TCP连接; 第二个用于发送请求并让响应开始返回; 还需传完对象. TCP的第三次握手报文可与HTTP请求一起发送, 不必再加一个完整RTT.

> **补充: 多对象时间.** 设共需获取 $m$ 个对象, 来自同一服务器, 且对象传输时间可相加:
>
> | 模型                                     | 近似总时间                                          |
> | ---------------------------------------- | --------------------------------------------------- |
> | 非持续连接, 逐个获取                     | $2mRTT+\sum_i t_i$                                  |
> | 持续连接, 不使用流水线, 逐个请求         | $(m+1)RTT+\sum_i t_i$                               |
> | 持续连接, 基础HTML后对其余对象流水线请求 | $3RTT+\sum_i t_i$, 适用于至少一个引用对象的理想模型 |
>
> 最后一行包含: 建连1个RTT, 取基础HTML1个RTT, 发送一组引用对象请求并开始收到响应1个RTT. 必须先读到HTML才能知道引用对象, 不能无条件把整个网页算成1个RTT.

**持续连接不等于流水线(pipelining)**: 前者复用连接, 后者允许前一个响应尚未回来就发出后续请求. 并行TCP连接, 不同服务器, 对象依赖, 瓶颈竞争等条件都会改变计算, 需依据题设画出先后关系.

**SP** 是空格, ASCII值0x20;**CR** 是回车(Carriage Return), 值0x0D;**LF** 是换行(Line Feed), 值0x0A.**OWS** 是可选空白(Optional Whitespace), 可由空格或水平制表符组成.

首部行结束采用CRLF(`\r\n`), 空行标志首部结束. 请求行包含方法, 请求目标和版本. HTTP/1.x首部采用文本格式, 但消息体可以是二进制数据; 不能把整个HTTP响应都当成ASCII文本.

| 方法(method) | 用途                                            |
| ------------ | ----------------------------------------------- |
| GET          | 获取资源; 查询参数可以放在URL的 `?` 后          |
| HEAD         | 与GET类似, 但不返回响应消息体, 常用于查询元数据 |
| POST         | 提交数据, 请求体可携带表单或其他内容            |
| PUT          | 创建或用请求体替换目标资源的表示                |

POST把数据放在消息体里, 并不自动提供加密. GET与POST的安全性不能仅由"参数放在哪里"判断.

响应由 **状态行, 首部行, 空行, 可选消息体** 组成:

```http
HTTP/1.1 200 OK
Content-Type: text/html; charset=UTF-8
Content-Length: 5

hello
```

`Content-Type`说明内容类型; `Content-Length`以byte计消息体长度; `Last-Modified`和`ETag`可用于缓存验证. 上面的结构是HTTP/1.x文本示例, HTTP/2和HTTP/3的线上编码不同.

| 状态码类别/例子                     | 含义                                             |
| ----------------------------------- | ------------------------------------------------ |
| 1xx                                 | 信息性响应                                       |
| 2xx; 200 OK                         | 成功                                             |
| 3xx; 301 Moved Permanently          | 重定向; 301通常用 `Location` 指明新位置          |
| 304 Not Modified                    | 条件请求确认缓存仍可使用, 无需重传对象消息体     |
| 4xx; 400 Bad Request, 404 Not Found | 请求错误; 400表示请求有问题,404表示资源未找到    |
| 5xx; 502 Bad Gateway                | 服务器侧错误; 502表示网关/代理从上游收到无效响应 |

## 2.3 HTTP状态与Cookie

服务器处理一个 HTTP 请求时, 协议本身不要求它记住此前的会话历史, 因此 HTTP 称为 **无状态协议(stateless protocol)**. 网站仍然可以登录或保存购物车, 只是需要应用另外记录这些状态, 并把后续请求与它们关联起来.

**Cookie** 使不同请求可以关联到同一个用户或会话. 一种基于会话标识的实现包含四部分:

1. 服务器在响应中用 `Set-Cookie` 设置标识.
2. 浏览器保存Cookie.
3. 浏览器后续向适用站点发送请求时用 `Cookie` 携带标识.
4. 服务器通过标识查询后台记录, 恢复购物车, 登录等状态.

```text
首次请求 → 服务器建立会话记录 → Set-Cookie: sid=1678
后续请求 → Cookie: sid=1678     → 服务器查找会话1678
```

在这种实现里, Cookie可以只存会话标识, 具体数据存于服务器. Cookie与服务器会话(session)不是同一个东西; Cookie也不负责保证交易原子性或故障恢复.

**第一方Cookie(first-party cookie)** 与用户正在访问的站点相关;**第三方Cookie(third-party cookie)** 可由页面中加载的其他站点资源设置或使用. 若多个页面加载同一个追踪服务, 并且浏览器允许发送其Cookie, 该服务便可将跨站请求关联起来. 这里记录机制, 浏览器政策和法规细节不作为固定知识结论.

## 2.4 Web缓存与条件请求

**Web缓存(Web cache)** 保存对象副本, 尽量在靠近用户的位置响应请求. 以代理缓存(proxy cache)为例: 对浏览器它是服务器, 对源服务器(origin server)它是客户端.

基本过程: 收到请求 → 检查可用副本 → 命中则返回; 未命中则向源站请求 → 缓存符合条件的响应 → 返回客户端. 是否能缓存, 能保存多久由相关规则与响应首部约束, 不是所有响应都可任意缓存.

缓存有两方面收益: 命中请求缩短路径; 减少接入链路负载, 从而也可能减少 **未命中请求** 的排队时延.

### 缓存性能计算

设请求率为 $\lambda$ request/s, 平均对象大小为 $L$ bit, 接入链路速率为 $R$ bit/s; 忽略请求, 首部和验证流量, 无缓存时

$$
\rho=\frac{\lambda L}{R}.
$$

若请求命中率为 $h$, 且命中与未命中的平均对象大小相同, 则

$$
\rho_{\mathrm{cache}}=\frac{(1-h)\lambda L}{R},\qquad
\bar T=hT_{\mathrm{hit}}+(1-h)T_{\mathrm{miss}}.
$$

如果对象大小差异显著, 应使用 **按字节统计的命中比例** 计算链路负载, 不能直接用请求命中率替代.

> **例.** 接入链路 $R=1.54$ Mbit/s, 平均对象大小 $L=100$ Kbit, 请求率 $\lambda=15$/s. 无缓存时平均流量为 $15\times100\times10^3=1.5\times10^6$ bit/s, 利用率 $\rho=1.5/1.54\approx0.974$.
>
> 若命中率 $h=0.4$, 且命中与未命中对象的平均大小相同, 接入链路流量降为 $0.6\times1.5=0.9$ Mbit/s, 利用率约 $0.584$.
>
> 再假设未命中请求的平均时延为 $2.01$ s, 命中请求为 $0.005$ s, 则平均时延为 $0.6\times2.01+0.4\times0.005=1.208$ s, 约 $1.21$ s. 这两个时延是额外给定条件, 不能仅由链路利用率推出.

### 条件GET(conditional GET)

缓存副本可能过期. 验证机制用小请求确认副本是否改变, 避免每次都重新下载完整对象:

| 阶段     | 消息/处理                                   |
| -------- | ------------------------------------------- |
| 初次获取 | 服务器返回对象及 `Last-Modified` 等验证信息 |
| 后续验证 | 缓存发送 `If-Modified-Since: <日期>`        |
| 未改变   | 返回 `304 Not Modified`, 缓存使用原副本     |
| 已改变   | 返回 `200 OK` 及新对象, 缓存更新副本        |

> **补充**: 也可用实体标签(entity tag, ETag)与 `If-None-Match` 验证.304省去的是对象消息体传输, 仍然有请求, 响应首部及往返时延; 缓存若仍满足新鲜度规则, 也可能直接使用而无需验证.

## 2.5 HTTP/2, HTTP/3与队头阻塞

后面的工作已经准备好, 却必须等前面的工作完成, 就会出现 **队头阻塞(Head-of-Line blocking, HOL blocking)**. HTTP 的响应顺序和 TCP 的字节交付顺序都可能造成等待, 但发生的位置不同, 解决方法也不同.

### HTTP/1.1的响应顺序

同一连接上的流水线请求需要按请求顺序返回响应. 若先请求一个大对象, 再请求多个小对象, 小对象会等待前面的响应. 持续连接减少握手, 仍不能消除这一顺序约束.

### HTTP/2的帧与多路复用

HTTP/2将消息拆为 **帧(frame)**, 不同流(stream)的帧可在同一连接上交错发送. 小对象不必等大对象完整传输后才开始返回, 缓解HTTP层的队头阻塞.

HTTP/2还包括优先级调度, 服务器推送(server push)和首部压缩等设计. 它们是协议能力, 不意味着所有实现都会采用所有功能. HTTP/2保留方法, 状态码等HTTP语义, 改变传输组织和编码方式.

**TCP层的阻塞仍在**: 同一TCP连接是一个有序字节流. 前面的字节丢失时, 后续字节即使已经到达, 也不能越过缺口按正常顺序交付给HTTP层, 因此同连接上的不同HTTP流都可能受影响.

### HTTP/3与QUIC

HTTP/3在QUIC上运行, QUIC使用UDP作为底层承载, 提供可靠流, 加密, 连接管理与拥塞控制. 不同流分别维护有序交付, 某流缺数据不会因单一TCP字节流的顺序要求直接阻挡其他流.

**边界**: 受损流仍需等待自己的缺失数据; 不同流仍共享连接的拥塞控制和网络资源. 因此, 独立流避免的是跨流的有序交付等待, 丢包导致的连接降速仍可能影响多个流.

| 版本           | 传输组织                    | 主要阻塞位置                           |
| -------------- | --------------------------- | -------------------------------------- |
| HTTP/1.1流水线 | 同一连接中按顺序返回响应    | HTTP响应顺序及TCP有序交付              |
| HTTP/2         | 多个流的帧交错, 共用TCP连接 | TCP丢失字节造成的跨流等待              |
| HTTP/3         | 多个QUIC流, UDP承载         | 各流内部顺序等待; 仍共享拥塞与资源约束 |

## 2.6 电子邮件: 传送与访问

邮件系统包含 **用户代理(User Agent, UA)**, 邮件服务器(mail server)及邮件传送协议. 服务器保存收件邮箱(mailbox)和待发送消息队列(outgoing message queue).

### SMTP发送链路

**简单邮件传送协议(Simple Mail Transfer Protocol, SMTP)** 用于提交, 传送邮件. 服务器间传送通常使用TCP 25端口.

```text
Alice的用户代理 → Alice的邮件服务器 → Bob的邮件服务器 → Bob的用户代理
       提交邮件           SMTP传送             邮件访问
```

接收方不必在发送时在线: Bob的邮件服务器先保存邮件, Bob稍后再读取. 发信服务器在SMTP会话中扮演客户端, 收信服务器扮演服务器.

SMTP交互分为问候, 邮件传送, 会话关闭:

| 命令/响应           | 作用                                       |
| ------------------- | ------------------------------------------ |
| `220`               | 服务器就绪                                 |
| `HELO`/`EHLO`,`250` | 客户端问候; EHLO还用于协商扩展             |
| `MAIL FROM:<...>`   | 指定信封发件人                             |
| `RCPT TO:<...>`     | 指定信封收件人, 可以有多个                 |
| `DATA`,`354`        | 进入邮件内容传输阶段                       |
| 单独一行 `.`        | 结束DATA内容; 完整终止序列为CRLF, 点, CRLF |
| `250`               | 服务器接受邮件                             |
| `QUIT`,`221`        | 关闭SMTP会话                               |

基础SMTP限制消息使用7-bit ASCII.**补充**: 非ASCII文字, 图片和附件可通过多用途因特网邮件扩展(Multipurpose Internet Mail Extensions, MIME)组织和编码; 扩展SMTP也可协商额外能力. 因此不能据此得出"邮件只能包含英文文本".

### 信封与邮件内容

SMTP命令 `MAIL FROM`, `RCPT TO`属于传送过程中的 **信封(envelope)**; 邮件内容里的 `From:`, `To:`, `Subject:`是 **消息首部(message header)**.

消息首部后接空行, 再接正文(body). 信封决定传送对象, 消息首部供邮件阅读与展示; 两者不是同一组字段, 例如密送收件人不必出现在展示的 `To:` 中.

### 读取邮件

- **因特网消息访问协议(Internet Message Access Protocol, IMAP)**: 邮件保存在服务器, 支持读取, 删除, 文件夹等管理操作, 适合跨设备访问.
- **邮局协议(Post Office Protocol, POP, 常见POP3)**: 主要用于获取邮件, 管理模型比IMAP简单.
- Web邮箱使用HTTP/HTTPS与浏览器交互, 后台再承担邮件传送和存储功能; 不是用SMTP把邮箱列表直接显示在浏览器里.

HTTP与SMTP都采用请求/命令及响应交互, 但HTTP获取资源通常是客户端 **拉取(pull)**, SMTP传送邮件是发送方 **推送(push)**.SMTP负责传送到邮箱服务器, 邮件访问协议负责用户读取, 不能混用.

## 2.7 域名系统DNS

浏览器知道网站的域名, 还需要查到可以连接的地址. **域名系统(Domain Name System, DNS)** 保存这类记录, 并提供查询协议. 记录分散在有层次关系的服务器上, 还可用于查询别名, 邮件服务器等信息, 或配合一定的负载分配.

域名便于人使用, IP地址用于网络交付. 同一名字可以对应多个地址, 同一地址也可以服务多个名字,**DNS映射不是一一对应关系**.

集中保存所有记录会造成单点故障, 流量瓶颈, 远距离查询和管理困难, 因此采用分层管理与缓存.

### 服务器层次

| 类型                                                            | 作用                                       |
| --------------------------------------------------------------- | ------------------------------------------ |
| 根服务器(root name server)                                      | 给出顶级域服务器的委派信息                 |
| 顶级域服务器(Top-Level Domain server, TLD server)               | 管理 `.com`, `.cn` 等顶级域的委派          |
| 权威服务器(authoritative name server)                           | 为其负责的域/区域提供权威记录              |
| 本地DNS服务器/递归解析器(local DNS server / recursive resolver) | 接受用户查询, 利用缓存或继续查询其他服务器 |

本地解析器不严格属于根→TLD→权威这一层次. 根服务器通常不直接保存每个网站的IP地址; 常见查询逐级获得下一层信息. 根服务是分布式部署,"若干逻辑服务器标识"不能解释成全球只有若干台物理机器.

### 迭代查询与递归查询

**迭代查询(iterative query)**: 被询问服务器返回答案或下一步该询问谁, 由询问者继续查询.

**递归查询(recursive query)**: 被询问服务器承担后续解析工作, 再向询问者返回结果.

常见组合是: 主机向本地解析器提出递归请求, 本地解析器对根, TLD及权威服务器进行迭代查询. 主机无需自己逐级联系所有服务器; 根和TLD也无需替每个用户完成全部后续查询. 这两种查询方式发生在不同通信环节, 可以同时存在.

无缓存的简化过程:

```text
主机 → 本地解析器: 查询 www.example.com
本地解析器 → 根: 得到 .com 服务器信息
本地解析器 → .com: 得到 example.com 权威服务器信息
本地解析器 → 权威: 得到 www.example.com 的地址
本地解析器 → 主机: 返回结果
```

箭头代表查询阶段, 每阶段还包含返回消息. 实际可有缓存, 别名和额外委派, 不能认为所有域名都固定经历三次外部查询.

**补充计算.** 若解析器必须串行查询 $q$ 个服务器, 每次RTT为 $RTT_i$, 忽略处理且无重试, 则外部查询时间约为 $\sum_i RTT_i$; 主机到解析器的往返另计. 加到HTTP时间时, 应先确认题目是否已经给出DNS耗时.

### 缓存与TTL

解析器获得记录后可按 **生存时间(Time To Live, TTL)** 缓存, 剩余TTL随时间递减. 缓存可降低时延和根服务器负载; 有效的TLD或权威委派缓存还可跳过前面的查询.

权威记录改变后, 旧缓存可能在TTL到期前继续返回旧值. DNS记录中的TTL是缓存时间, IP首部TTL约束转发跳数,**同名但含义不同**.

### 资源记录

**资源记录(Resource Record, RR)** 可概括为 `(name, value, type, ttl)`:

| 类型  | name      | value/用途                                       |
| ----- | --------- | ------------------------------------------------ |
| A     | 主机名    | IPv4地址                                         |
| AAAA  | 主机名    | IPv6地址                                         |
| NS    | 域/区域名 | 权威名字服务器的主机名                           |
| CNAME | 别名      | 规范名(canonical name), 还可能需要继续解析       |
| MX    | 邮件域名  | 邮件交换服务器的主机名及优先级; 不是直接存IP地址 |

例: `example.com`的MX指向`mail.example.com`, 再查询后者的A/AAAA得到地址. NS记录同样指向服务器名字; 额外地址记录可帮助解析器联系该服务器.

### DNS消息

查询和响应采用相同的总体结构:

- 首部包含16-bit标识(identification), 标志(flags)和各部分记录数; 响应用同一标识关联查询.
- 问题部分(question): 被查询名字, 类型等.
- 回答部分(answer): 答案记录.
- 权威部分(authority): 权威或委派相关信息.
- 附加部分(additional): 有助于后续处理的记录, 例如名字服务器地址.

标志可表示查询/响应, 期望递归(recursion desired), 可提供递归(recursion available)及权威应答(authoritative answer). 响应不一定来自权威服务器, 本地缓存也可回答.

传统DNS的小查询常用UDP 53.**补充**: DNS也使用TCP 53, 例如UDP响应被截断后可改用TCP; DNS不能概括成"只使用UDP".

### 注册与安全

一个域名要能被外部查询到, 上下级服务器之间需要接好委派关系. 注册商处理注册, 注册局维护相应顶级域; 顶级域的 NS 记录指向该域的权威服务器, 必要时还提供胶水地址记录. 权威服务器里再保存网站的 A/AAAA 和邮件的 MX 等记录. 只在本机写一条记录, 外部服务器还不知道该来哪里找它.

DNS攻击包括伪造响应, 缓存投毒(cache poisoning)和DDoS. 域名系统安全扩展(DNS Security Extensions, **DNSSEC**)用于验证DNS数据的来源与完整性, 不能简单等同于"加密DNS查询". 缓存和分布式副本有助于降低部分攻击影响, 但不意味着DNS不会受到攻击.

## 2.8 P2P文件分发与BitTorrent

### 分发时间的瓶颈

设文件为 $F$ bit, 要分发给 $N$ 个用户; 服务器上传速率为 $u_s$, 用户 $i$ 的上传, 下载速率分别为 $u_i,d_i$, 且 $d_{\min}=\min_i d_i$. 忽略传播, 控制开销, 内部网络瓶颈, 允许理想并行调度.

**客户端-服务器分发.** 服务器必须上传 $N$ 份, 最慢用户必须下载一份, 因此

$$
D_{\mathrm{CS}}\ge\max\left(\frac{NF}{u_s},\frac{F}{d_{\min}}\right).
$$

**P2P分发.** 服务器至少上传一份原始信息; 每名用户至少下载一份; 全体用户总共需要接收 $NF$ bit, 可用总上传容量为 $u_s+\sum_i u_i$, 因此

$$
D_{\mathrm{P2P}}\ge\max\left(
\frac{F}{u_s},\frac{F}{d_{\min}},\frac{NF}{u_s+\sum_i u_i}
\right).
$$

这些首先是 **下界**: 任何方案都不能突破相应资源限制; 在允许文件任意细分, 节点持续在线, 各上传链路能被理想调度且无其他瓶颈的流体模型中, 可用它们描述理想最小分发时间. 真实系统受块可用性, 节点离开和调度开销影响, 未必达到下界.

**为什么取最大值而不是求和?** 服务器上传, 用户下载以及对等方交换可重叠进行, 不要求三个阶段依次发生; 最紧的容量约束决定完成时间下界.

**例.** 若每名用户上传 $u$,$F/u=1$ h,$u_s=10u$,$d_{\min}\ge u_s$:

$$
D_{\mathrm{CS}}\ge\max(N/10,0.1)\text{ h},\qquad
D_{\mathrm{P2P}}\ge\max\left(0.1,\frac{N}{N+10}\right)\text{ h}.
$$

C/S的服务器上传需求随 $N$ 线性增加; P2P的用户增加也带来上传容量, 体现自扩展性(self-scalability).

### BitTorrent的块交换

BitTorrent将文件分为块(chunk), 同一文件的交换群体称 **torrent**. 跟踪器(tracker)提供参与者信息; 节点获得邻居列表后交换块, 下载过程中也上传已有块. 节点随时加入, 退出称为 **节点流动(churn)**.

两项关键策略:

1. **最稀缺优先(rarest first)**: 优先请求邻居中副本较少的缺失块, 避免部分块成为整个群体的瓶颈, 并增加块分布的多样性.
2. **互惠交换(tit-for-tat)与乐观疏通(optimistic unchoking)**: 优先向当前给自己较高下载速率的邻居上传; 周期性尝试新伙伴, 给尚未建立互惠关系的节点机会.

一种经典调度策略是定期重选4名高贡献伙伴, 每10秒评估, 每30秒乐观疏通一个额外伙伴. 这些参数描述这一策略的具体配置, 理解重点是"激励贡献"和"探索新伙伴", 不是认为所有实现必须永远采用同一参数.

## 2.9 视频流, DASH与CDN

### 编码与播放缓冲

视频是按时间顺序显示的图像帧. 编码利用 **空间冗余(spatial redundancy)** 和 **时间冗余(temporal redundancy)** 压缩数据.

- **固定码率(Constant Bit Rate, CBR)**: 编码输出速率较固定.
- **可变码率(Variable Bit Rate, VBR)**: 随画面复杂度等变化.

码率(bit rate)不是帧率(frame rate): 前者为bit/s, 后者为frame/s. 相同帧率可以有不同码率和画质.

**存储视频流式播放(streaming stored video)** 允许客户端播放前面的内容, 同时继续下载后面的内容. 连续播放需要按原时间节奏消耗视频, 但网络到达有波动, 称 **时延抖动(delay jitter)**.

客户端用 **播放缓冲(playout buffer)** 吸收波动: 先积累数据, 再开始播放. 缓冲增大可降低短暂波动造成的卡顿, 但增加启动等待.

**补充关系.** 若当前缓冲量为 $B$ bit, 下载速率为 $x$ bit/s, 播放消耗码率为 $r$ bit/s, 在恒定速率区间内

$$
\frac{dB}{dt}=x-r.
$$

若 $x<r$, 缓冲将在约 $B/(r-x)$ 秒后耗尽. 缓冲可以抵抗短时不足, 不能解决长期下载能力低于播放码率的问题.

### DASH自适应流

**基于HTTP的动态自适应流(Dynamic Adaptive Streaming over HTTP, DASH)** 将视频切为时间段, 每段提供不同编码码率的版本.

服务器提供 **清单文件(manifest)**, 说明各段, 各码率版本的URL等信息. 客户端根据测得的带宽和缓冲情况, 逐段选择: 何时请求, 请求哪个码率, 从哪个服务器请求.

网络变差时选择较低码率, 网络改善且缓冲合适时选择较高码率. 客户端通过改变后续视频段的编码版本, 让下载需求适应可用带宽.

### CDN内容分发

**内容分发网络(Content Delivery Network, CDN)** 在多个地点部署内容副本, 避免所有用户连接一个远处的大服务器, 降低单点故障, 长路径和集中拥塞风险.

有两种部署思路:

- **深入接入网(enter deep)**: 部署点多, 更靠近用户, 管理和维护复杂.
- **集中于接入网附近(bring home)**: 较少的大型集群部署在靠近接入网络的PoP, 便于集中维护.

用户选择哪个CDN节点可由DNS引导. 典型过程: 解析内容域名 → 获得指向CDN名字的CNAME → CDN的DNS返回合适节点的地址 → 客户端向该节点发送HTTP请求.

DNS解析URL中的 **域名**, HTTP请求携带资源路径. 所谓"最近节点"也不必是地理距离最短, 而是依据网络位置, 负载等选择.

视频服务可将这些机制结合: **编码** 减小数据量;**DASH** 适应带宽;**缓冲** 抵抗短时波动;**CDN** 改善内容位置与分发容量. 它们解决不同问题.

## 2.10 Socket编程中的UDP与TCP

以下用Python 3说明基本接口流程. UDP按数据报收发, TCP按字节流收发; 消息完整性和应用协议边界需分别处理.

### UDP: 按数据报收发

```python
# 服务器的核心流程
from socket import socket, AF_INET, SOCK_DGRAM

sock = socket(AF_INET, SOCK_DGRAM)
sock.bind(("", 12000))
while True:
    data, client_addr = sock.recvfrom(2048)
    sock.sendto(data.decode().upper().encode(), client_addr)
```

客户端创建UDP socket, 用 `sendto(data, (server, port))`发送, 用 `recvfrom(...)`接收.`recvfrom`同时返回发送方地址, 服务器用该地址回复.

UDP保持数据报边界; 一条消息的数据报可能丢失或乱序. 接收缓冲参数必须足够容纳消息, 否则可能截断; 应用若需要超时, 重试或顺序管理, 必须额外实现.

### TCP: 监听socket与连接socket

服务器流程: `socket` → `bind` → `listen` → `accept` → 在返回的连接socket上收发 → 关闭连接socket. 监听socket可继续接受其他连接.

客户端流程: `socket(AF_INET, SOCK_STREAM)` → `connect((server, port))` → 收发 → `close`. 地址在连接建立时确定, 不必每次发送都指定目的地址.

```python
# 服务器的一次连接处理; 消息结束规则需由应用协议另行规定
from socket import socket, AF_INET, SOCK_STREAM

listener = socket(AF_INET, SOCK_STREAM)
listener.bind(("", 12000))
listener.listen(5)
conn, client_addr = listener.accept()
# 此后对 conn 使用 recv / sendall,而不是对 listener 收发应用数据
```

**TCP没有消息边界.** 一次 `send` 不保证对应一次 `recv`: 接收可能只拿到部分内容, 也可能一次拿到多次发送的数据. 应用需用固定长度, 长度前缀或分隔符定义完整消息, 并循环接收.

`send` 返回本次接受发送的字节数, 可能没有接收全部传入数据; Python 的 `sendall` 会继续发送剩余部分. `recv` 返回空字节串, 通常表示对端已关闭发送方向.

`listen` 的参数则与待接受连接的队列有关, 不是服务器一生能服务的客户端总数.

### 小实验: 用长度前缀接收完整消息

将下面代码保存为 `tcp_message.py`. 应用协议约定: 前4 byte是大端无符号整数, 表示正文的字节数; 后面跟UTF-8正文. 示例只监听本机, 每条消息最多1 MiB.

```python
import socket
import struct
import sys

ADDRESS = ("127.0.0.1", 12000)
MAX_MESSAGE = 1024 * 1024


def recv_exact(conn, size):
    data = bytearray()
    while len(data) < size:
        chunk = conn.recv(size - len(data))
        if not chunk:
            raise EOFError("连接在消息接收完成前结束")
        data.extend(chunk)
    return bytes(data)


def recv_message(conn):
    size = struct.unpack("!I", recv_exact(conn, 4))[0]
    if size > MAX_MESSAGE:
        raise ValueError("消息过大")
    return recv_exact(conn, size).decode("utf-8")


def encode_message(text):
    body = text.encode("utf-8")
    if len(body) > MAX_MESSAGE:
        raise ValueError("消息过大")
    return struct.pack("!I", len(body)) + body


def main(mode):
    if mode == "server":
        with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as listener:
            listener.bind(ADDRESS)
            listener.listen(1)
            print("等待本机客户端连接", flush=True)
            conn, _ = listener.accept()
            with conn:
                conn.settimeout(5)
                for _ in range(2):
                    text = recv_message(conn)
                    conn.sendall(encode_message(text.upper()))
    elif mode == "client":
        with socket.create_connection(ADDRESS, timeout=5) as conn:
            first = encode_message("hello 网络")
            second = encode_message("second message")
            # 故意拆开首条消息的长度字段, 再合并后续数据发送.
            conn.sendall(first[:2])
            conn.sendall(first[2:] + second)
            print(recv_message(conn))
            print(recv_message(conn))
    else:
        raise SystemExit("用法: python tcp_message.py server|client")


if __name__ == "__main__":
    main(sys.argv[1] if len(sys.argv) == 2 else "")
```

先在一个终端运行 `python tcp_message.py server`, 再在另一个终端运行 `python tcp_message.py client`. 客户端预期输出:

```text
HELLO 网络
SECOND MESSAGE
```

两次`sendall`既拆开了第一条消息, 又把两条消息的部分内容合在一次发送中. 接收端依靠长度前缀恢复边界, 与每次`recv`实际返回多少字节无关. 本机运行时数据可能被一次读齐; 即使没有观察到多次接收, 也仍需要循环处理短读.

**动手改一处.** 把`recv_exact`中的接收长度改成`min(3, size - len(data))`, 强制每次最多读取3 byte, 再运行. 输出应保持一致. 接着思考: 若正文长度误用`len(text)`而非`len(body)`, 中文消息会怎样影响下一条消息的解析?
