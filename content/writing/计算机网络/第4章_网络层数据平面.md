## 4.1 数据平面与控制平面

网络层把运输层报文段封装进IP数据报, 在不同网络之间完成主机到主机交付. 发送端和接收端运行IP, 路由器则检查经过的IP分组, 决定下一步怎样处理.

**数据平面(data plane)** 解决单个分组到达后如何处理的问题, 包括查表, 转发, 排队, 丢弃和修改首部. **控制平面(control plane)** 计算与维护这些处理规则, 包括选择路由, 分发可达性信息和下发流表.

| 概念                                           | 范围                     | 结果                       |
| ---------------------------------------------- | ------------------------ | -------------------------- |
| 转发(forwarding)                               | 单台设备的局部动作       | 把到达分组送到合适输出端口 |
| 路由(routing)                                  | 网络范围的路径选择       | 形成可用于转发的路径和表项 |
| 传统分布式控制                                 | 各路由器交换信息并计算   | 每台路由器生成自己的转发表 |
| 软件定义网络(Software-Defined Networking, SDN) | 逻辑集中的控制器管理网络 | 控制器计算并向设备安装规则 |

逻辑集中不要求只有一台物理服务器. 同样, 路由器可以继续按已有表项快速转发, 不必为每个分组实时运行一次路由算法.

### 网络服务模型

基础IP提供 **尽力而为(best effort)** 服务: 不保证交付成功, 有序, 固定时延或最低带宽. 这种简单模型便于连接不同链路, 但端系统必须处理可能的丢失与波动.

**服务质量(Quality of Service, QoS)** 描述时延, 吞吐量, 丢失等方面的服务要求. 集成服务(Integrated Services, IntServ)可对流进行资源预留; 区分服务(Differentiated Services, DiffServ)按类别提供不同待遇. 给分组标记优先级本身不等于已经获得端到端保证, 路径中的设备还要配置相应资源和策略.

## 4.2 路由器结构与最长前缀匹配

典型路由器包含输入端口, 交换结构(switching fabric), 输出端口和路由处理器(routing processor).

1. 输入端口完成物理接收, 链路层检错与解封装, 获得IP分组.
2. 根据首部查表, 确定输出端口或其他动作.
3. 交换结构将分组从输入侧送到输出侧.
4. 输出侧排队, 调度, 加上新链路的封装并发送.

数据平面通常使用专用硬件实现高速处理; 路由处理器运行控制与管理功能. 转发表可复制到各输入端口, 避免每个分组都依赖一个中央处理器查表.

### 最长前缀匹配

目的地址转发(destination-based forwarding)根据目的IP地址查表. 一条前缀长度为 $p$ 的规则, 要求目的地址的前 $p$ bit与规则一致.

**最长前缀匹配(Longest Prefix Match, LPM)**: 多条规则同时匹配时, 选前缀最长的一条. 它表示更具体的地址范围, 不是最长字符串或数值最大的IP地址.

> **例.** 转发表包含:
>
> | 前缀               | 输出     |
> | ------------------ | -------- |
> | `0.0.0.0/0`        | 默认出口 |
> | `200.23.16.0/20`   | A        |
> | `200.23.18.0/23`   | B        |
> | `200.23.18.128/25` | C        |
>
> `200.23.18.140`匹配后三条, 选C. `200.23.19.7`选B. `200.23.22.1`选A. `203.0.113.9`仅匹配默认路由.

三态内容寻址存储器(Ternary Content-Addressable Memory, TCAM)可用0, 1和通配位表示规则, 支持高速并行匹配. LPM是转发语义, TCAM是实现手段, 两者不能等同.

### 交换结构

| 类型                              | 传输方式                           | 主要瓶颈                         |
| --------------------------------- | ---------------------------------- | -------------------------------- |
| 经内存交换(memory switching)      | 先写入共享内存, 再读到输出侧       | 内存与总线带宽, 每个分组需要读写 |
| 经总线交换(bus switching)         | 多个端口共享内部总线               | 总线竞争与总容量                 |
| 互联网络(interconnection network) | 交叉开关(crossbar), Clos等多级结构 | 端口争用和内部路径安排           |

设有 $N$ 个输入, 每个线速为 $R$, 如果所有输入都持续接收, 理想交换总能力需要达到 $NR$. 这不能消除多个输入同时争用同一条速率为 $R$ 的输出链路的问题.

多级结构可以并行传输发往不同输出的分组. 有些设备将分组切成固定长度单元进入交换结构, 在输出侧重组; 这不是IP层的跨网络分片.

## 4.3 排队, 缓冲与调度

### 输入排队与HOL阻塞

如果交换结构来不及接收, 或多个输入争用同一输出, 分组会在输入侧等待. 若采用单个FIFO输入队列, 队首分组的输出繁忙, 即使后面分组对应的输出空闲, 也无法越过队首.

这种 **队头阻塞(Head-of-Line blocking, HOL blocking)** 来自输入队列的处理顺序. 它与HTTP响应顺序, TCP有序字节流中的HOL发生在不同位置, 共同点都是前面的工作阻止后续工作推进.

### 输出排队与缓冲膨胀

当交换结构送往某个输出的数据速率短时超过出链路速率, 输出队列增长. 缓冲可以吸收突发, 但不能提高瓶颈链路的长期发送能力.

一种传统缓冲经验估计是 $B\approx C\times RTT$, 其中 $C$为瓶颈链路速率. 在许多相互独立, 不同步的长连接共享链路等条件下, 也有 $B\approx C\times RTT/\sqrt N$的估计. 二者是特定工作负载下的经验尺度, 不是任意网络的容量定理.

过大的队列会造成 **缓冲膨胀(bufferbloat)**: 负载变化主要表现为长时间排队, RTT增大, 实时交互变差. 因此缓冲目标不是越大越好, 而是兼顾链路利用率, 突发容忍和排队时延.

### 缓冲管理与发送调度

缓冲管理(buffer management)决定接收, 丢弃或标记哪些分组; 调度(scheduling)决定已经排队的分组谁先发送.

- **尾丢弃(tail drop)**: 队列满后丢掉新到分组.
- **优先级丢弃**: 优先保留某些类别, 丢弃较低优先级分组.
- **随机早期检测(Random Early Detection, RED)**: 在队列尚未完全填满时, 依据平均队列状态提前随机丢弃或配合ECN标记, 提供拥塞反馈.

| 调度                                     | 工作方式                     | 注意点                                             |
| ---------------------------------------- | ---------------------------- | -------------------------------------------------- |
| FIFO / FCFS                              | 按到达顺序发送               | 简单, 不区分类别                                   |
| 严格优先级(priority scheduling)          | 先服务最高的非空队列         | 高优先级持续繁忙时, 低优先级可能饥饿               |
| 轮询(Round Robin, RR)                    | 每轮从各非空队列取一整个分组 | 若分组长度不同, 每轮分组数相同不等于字节份额相同   |
| 加权公平排队(Weighted Fair Queuing, WFQ) | 近似按权重分配服务           | 以字节服务量为基础, 不是简单每轮发送同样数量的分组 |

若活跃类别权重为 $w_i$, 理想加权服务中类别 $i$的份额约为 $w_i/\sum_jw_j$. 在容量 $C$上, 权重1, 2, 1且始终有积压的三个类别约分得 $C/4, C/2, C/4$. 空队列不必浪费其份额; 实际保证还取决于调度与流量约束.

网络中立(network neutrality)讨论运营者如何区别对待不同流量. 调度与缓冲是实现差别待遇的技术手段, 是否允许及如何约束属于政策问题, 不能由某个调度算法直接决定.

## 4.4 IPv4数据报与分片

**网际协议第4版(Internet Protocol version 4, IPv4)** 使用32-bit地址. 基本首部20 byte, 有选项时最长60 byte.

| 字段                 | 长度      | 含义                                                 |
| -------------------- | --------- | ---------------------------------------------------- |
| Version              | 4 bit     | IPv4为4                                              |
| IHL                  | 4 bit     | 首部长度, 单位4 byte; 基本首部的值为5                |
| DSCP / ECN           | 6 / 2 bit | 服务类别标记与显式拥塞通知                           |
| Total Length         | 16 bit    | 整个IP数据报长度, 包括首部, 单位byte                 |
| Identification       | 16 bit    | 与源, 目的地址和协议等配合, 关联同一原始数据报的分片 |
| Flags                | 3 bit     | 包含DF禁止分片, MF后面还有分片等标志                 |
| Fragment Offset      | 13 bit    | 本片数据相对原始IP负载起点的偏移, 单位8 byte         |
| TTL                  | 8 bit     | 每经过路由器递减, 防止分组无限循环                   |
| Protocol             | 8 bit     | 上层协议编号, TCP为6, UDP为17, ICMP为1               |
| Header Checksum      | 16 bit    | 只校验IPv4首部; TTL变化后要更新                      |
| Source / Destination | 各32 bit  | 源与目的IPv4地址                                     |
| Options / Padding    | 可变      | 选项与4-byte对齐填充                                 |

Total Length最大为65535 byte, 包含IP首部, 不能当作全部应用数据. Protocol指出把IP负载交给哪个上层协议, 不等同于TCP/UDP端口号.

### 分片计算

**最大传输单元(Maximum Transmission Unit, MTU)** 是某条链路能够承载的IP分组大小上限. 数据报过大时, IPv4可在允许分片的条件下拆成多个分片, 每片都带IP首部, 最终由目的端重组.

设原始总长度为 $L$, 每片首部长度为 $H$, 出链路MTU为 $M$. 非最后一片的数据长度必须为8 byte的整数倍, 最大取

$$
D=8\left\lfloor\frac{M-H}{8}\right\rfloor.
$$

> **例.** 原始数据报4000 byte, 首部20 byte, MTU=1500 byte. 原始负载为3980 byte, 每个非末片最多1480 byte.
>
> | 分片 | 数据长度 | IP总长度 | Offset | MF  |
> | ---- | -------- | -------- | ------ | --- |
> | 1    | 1480     | 1500     | 0      | 1   |
> | 2    | 1480     | 1500     | 185    | 1   |
> | 3    | 1020     | 1040     | 370    | 0   |
>
> 偏移分别为 $0/8, 1480/8, 2960/8$. 三片Identification相同. 总传输长度为4040 byte, 因为新增了两个首部.

MF=0只说明它是原始数据报的末片, 不说明这一片前面没有其他分片. DF=1而出链路不能承载时, 路由器不能擅自分片, 通常丢弃并返回相应ICMP信息. 分片丢失后不能靠其余分片完整恢复原数据报.

## 4.5 IPv4地址, 子网与CIDR

IP地址分配给 **接口(interface)**. 一台路由器通常有多个接口, 各接口可属于不同子网; 不能把一台机器和一个IP地址机械地一一对应.

IPv4点分十进制(dotted decimal)将32 bit分成四个8-bit段, 每段0到255. **无类别域间路由(Classless Inter-Domain Routing, CIDR)** 使用 `a.b.c.d/p`, 其中 $p$是网络前缀长度, 不要求落在8-bit边界.

**子网掩码(subnet mask)** 的前 $p$ bit为1, 其余为0. IP地址与掩码按位与, 得到网络地址.

$$
\text{网络地址}=\text{IP地址}\ \mathrm{AND}\ \text{子网掩码}.
$$

一个 `/p`地址块包含 $2^{32-p}$个地址. 普通广播子网中, 全0主机部分为网络地址, 全1为子网定向广播地址, 通常可分配主机数为 $2^{32-p}-2$. 这不是所有前缀的通用减2规则: `/31`点对点链路和`/32`主机路由有专门语义.

> **例.** `192.0.2.130/26`的掩码为`255.255.255.192`. 最后一段块长64, 网络地址为`192.0.2.128`, 广播地址为`192.0.2.191`, 普通主机范围为`.129`到`.190`, 共62个.

在简单的局域网模型中, 同子网接口无需经过IP路由器即可进行链路层通信. 路由器接口将不同IP子网连接起来. 主机发送前用掩码判断目的是否在本地子网: 本地目的直接寻找其链路层地址, 外部目的则把帧交给默认网关, IP目的地址仍是最终目的主机.

### 划分与聚合

将 `/p`地址块分成 $2^s$个等大小子块, 新前缀为 `/p+s`. 子块必须在相应大小的边界上对齐.

> **例.** `200.23.16.0/20`共4096个地址, 分成8个`/23`, 每块512个地址. 依次为第三段16, 18, 20, 22, 24, 26, 28, 30开头的地址块.

**路由聚合(route aggregation)** 用较短前缀概括连续且对齐的多个地址块, 减少外部表项. 若其中`200.23.18.0/23`改由另一运营商接入, 可以额外发布这条更具体的路由, LPM会让它覆盖原来的`/20`规则.

连续不等于一定能合并为一个前缀. 例如两个相邻地址块还必须共享足够长的前缀, 合并后的起点必须按新块大小对齐, 不能覆盖本不应包含的其他网络.

### 特殊地址

| 地址/范围         | 用途                                     |
| ----------------- | ---------------------------------------- |
| `0.0.0.0`         | 尚未配置地址等特定场景中的未指定源地址   |
| `0.0.0.0/0`       | 默认路由, 与单个`0.0.0.0`含义不同        |
| `127.0.0.0/8`     | 环回(loopback), 常用`127.0.0.1`          |
| `255.255.255.255` | 本地链路受限广播, 不作为普通目的主机地址 |
| `10.0.0.0/8`      | 私有地址                                 |
| `172.16.0.0/12`   | 私有地址, 不是整个`172.0.0.0/8`          |
| `192.168.0.0/16`  | 私有地址                                 |

私有地址可在不同组织重复使用, 不在公共因特网上作为可全球路由的内部地址发布.

## 4.6 DHCP动态配置

**动态主机配置协议(Dynamic Host Configuration Protocol, DHCP)** 为主机分配有期限的地址租约(lease), 并提供掩码, 默认网关, DNS服务器等参数. 地址到期需要续租或重新配置, 不是永久归主机所有.

初次加入网络且没有可用配置时, 常见过程为DORA:

| 阶段     | 消息                 | 作用                                               |
| -------- | -------------------- | -------------------------------------------------- |
| Discover | 客户端寻找服务器     | 尚无地址, 可用`0.0.0.0:68`发往`255.255.255.255:67` |
| Offer    | 服务器提出地址与租约 | 可以收到多个服务器的提议                           |
| Request  | 客户端选择并请求配置 | 初次选择时常广播, 也使其他服务器知道选择结果       |
| ACK      | 服务器确认租约       | 客户端根据有效确认完成配置                         |

DHCP使用UDP, 服务器端口67, 客户端端口68. 以太网广播目的MAC为`FF:FF:FF:FF:FF:FF`. IP广播与链路层广播是不同层次的字段, 在本地初次发现中可以配合使用.

并非所有DHCP交互都固定四次广播: 客户端记得旧租约, 续租, 使用中继(relay)等情况会改变过程. DHCP服务器也不必与默认网关位于同一设备. 客户端与服务器通过事务标识等信息关联一次交互, 不能只看某个广播目的地址判断消息属于谁.

## 4.7 NAT地址转换

**网络地址转换(Network Address Translation, NAT)** 修改经过设备的IP地址. 家用网络常用同时转换端口的 **网络地址端口转换(Network Address and Port Translation, NAPT)**, 让多台内部主机共享一个公网IPv4地址.

> **例.** 内部主机`10.0.0.1:3345`访问外部Web服务器, NAT分配公网映射`138.76.29.7:5001`.
>
> | 方向         | 转换前             | 转换后             |
> | ------------ | ------------------ | ------------------ |
> | 请求源端点   | `10.0.0.1:3345`    | `138.76.29.7:5001` |
> | 响应目的端点 | `138.76.29.7:5001` | `10.0.0.1:3345`    |

NAT保存状态表, 并更新受地址或端口修改影响的校验和. TCP与UDP有独立协议空间, 实际映射还可能考虑远端地址, 超时和实现策略.

多个内部连接需具有可区分的外部映射. 端口字段16 bit说明映射空间有限, 不代表一个公网地址在所有条件下都恰好支持65536条任意连接.

NAT减少公网地址需求, 也使内部地址规划相对独立. 但它改变端到端寻址, 使外部主动连接内部服务更复杂, 通常需要端口映射, 中继或穿透机制. **NAT不是身份认证或加密机制, 也不能替代防火墙策略.**

## 4.8 IPv6与隧道

**网际协议第6版(Internet Protocol version 6, IPv6)** 使用128-bit地址, 基本首部固定40 byte. 地址常以十六进制分组表示, 连续的全0组可用一次`::`压缩.

| 基本首部字段         | 长度      | 作用                                                  |
| -------------------- | --------- | ----------------------------------------------------- |
| Version              | 4 bit     | 值为6                                                 |
| Traffic Class        | 8 bit     | 包含流量类别及拥塞标记语义                            |
| Flow Label           | 20 bit    | 协助标识需要相应处理的流                              |
| Payload Length       | 16 bit    | 基本首部之后的长度, 包括扩展首部, 不含40-byte基本首部 |
| Next Header          | 8 bit     | 指向扩展首部或上层协议                                |
| Hop Limit            | 8 bit     | 类似IPv4 TTL的逐跳限制                                |
| Source / Destination | 各128 bit | 源与目的地址                                          |

IPv6基本首部没有首部校验和. 可选能力通过扩展首部(extension header)表达, 不是完全不能带选项. 中间路由器不执行IPv4式分片; 需要时由源端使用分片扩展首部, 接收端重组. 不能将其记成IPv6在任何情况下都没有分片. [IPv6首部与分片规范](https://www.rfc-editor.org/rfc/rfc8200.html)

### IPv6穿越IPv4网络

**隧道(tunneling)** 将整个IPv6分组作为IPv4负载:

```text
隧道入口前: [IPv6首部 | 上层数据]
IPv4网络内: [外层IPv4首部 | 内层IPv6首部 | 上层数据]
隧道出口后: [IPv6首部 | 上层数据]
```

内层源/目的地址标识真正通信的IPv6端点, 外层源/目的地址标识隧道入口和出口. IPv4核心按外层地址转发, 不需要理解内层IPv6. 隧道增加首部开销, 因而也要考虑实际可用MTU.

## 4.9 通用转发, SDN与中间设备

**通用转发(generalized forwarding)** 将设备动作抽象为 **匹配加动作(match + action)**. 匹配可以涉及输入端口, MAC地址, VLAN, IP前缀, IP协议及TCP/UDP端口等; 动作包括转发, 丢弃, 修改, 复制或送往控制器.

| 流表部分         | 含义                       |
| ---------------- | -------------------------- |
| 匹配模式(match)  | 哪些分组适用, 可包含通配符 |
| 优先级(priority) | 多条规则重叠时选择哪条     |
| 动作(action)     | 匹配后执行的操作           |
| 计数器(counter)  | 匹配分组数, 字节数等统计   |

例如, 匹配目的TCP端口22并丢弃, 可表达一种访问控制; 匹配目的MAC并输出端口, 类似交换机; 匹配IP前缀并转发, 类似路由器. **通用流表依规则优先级解决重叠, 不自动等同于所有字段都执行最长前缀匹配.**

OpenFlow提供控制器与转发设备交互的一种机制. 多台设备的流表需要协同, 才能产生完整路径; 单台设备某条正确规则不保证整条路径不存在环路或黑洞.

**中间设备(middlebox)** 执行超出普通IP转发的功能, 例如NAT, 防火墙, 入侵检测, 负载均衡, 代理缓存. 网络功能虚拟化(Network Functions Virtualization, NFV)将部分功能由专用设备转到软件和通用平台, 与SDN的控制/转发分离相互关联但不是同一概念.

### IP沙漏与端到端原则

IP形成协议栈的窄腰(thin waist): 上面可以有多种运输和应用协议, 下面可以有多种链路和物理介质, 它们通过共同的IP层互联.

**端到端原则(end-to-end argument)** 强调, 一些正确性要求只有端点掌握完整上下文才能最终保证. 例如每跳链路可靠传输仍不能排除端系统或中间处理中的其他丢失, 端到端可靠性仍需端点检验. 在网络内部增加功能可改善性能, 但不能因此省略最终必要的端点检查.
