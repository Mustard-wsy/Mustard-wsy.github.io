现在士兵能从[流场](/writing/pathfinding-03/)读取行进方向, 用[相对速度](/writing/pathfinding-04/)判断是否会撞到别人, 再由 [ORCA](/writing/pathfinding-05/)选择避让速度. 路会找了, 人也会让了, 接起来是否就能顺利穿过地图?

但如果所有人都被要求站在同一个点, 或两队人同时挤进只能容一人通过的门, 一个正确的避碰模块仍可能让大家停住. 系统还需要决定谁先走, 到哪里算完成, 以及执行器究竟听谁的.

## 1. 沿着一帧数据看各层分工

| 层             | 输入                         | 输出                         | 不负责什么             |
| -------------- | ---------------------------- | ---------------------------- | ---------------------- |
| 任务与目标分配 | 玩家指令, 编队, 交互需求     | 每人的目标点或可接受目标区域 | 几何避碰               |
| 全局导航       | 地形, 通行规则, 目标         | 路径通道或共享流场           | 给每对角色安排会面时间 |
| 路径跟随       | 当前位置, 路线, 到达状态     | 期望速度                     | 保证与邻居不相撞       |
| 局部避障       | 当前状态, 邻居, 墙, 期望速度 | 本轮可执行速度候选           | 全局绕路与通行调度     |
| 运动执行       | 选定速度, 碰撞与运动规则     | 实际位置和实际速度           | 重新决定任务目标       |

Flow Field 和 ORCA 可以组合, 也可以单独换掉其中一层. NavMesh 通道跟随同样能给 ORCA 提供期望速度. 不需要因为增加了局部避障, 就把整个世界改成网格.

在 RVO2 官方使用流程中, 调用方在每步前设置 preferred velocity, 再调用 `doStep()`. 目标和全局路线由外部应用管理, 静态障碍需要先登记并处理. 这些职责可对照[官方使用文档](https://gamma-web.iacs.umd.edu/RVO2/documentation/2.0/using.html).

## 2. 所有人先看同一时刻, 再一起移动

一个容易复现的问题是按数组顺序更新角色: 先计算 A 并立刻移动 A, 再计算 B. 这样 B 看到的是 A 的新状态, A 看到的却是 B 的旧状态. 仅改变遍历顺序, 结果就可能改变.

概念上的固定步长流程应是:

1. 固定这一轮的位置与实际速度快照, 建立邻域查询结构.
2. 为所有角色计算期望速度, 包括路径方向与到达减速.
3. 基于同一份快照为所有角色求解新速度.
4. 统一执行一个仿真步, 得到下一轮状态.
5. 渲染在相邻仿真状态间插值, 不把显示插值当成真实物理状态.

如果让 RVO2 在 `doStep()` 中推进位置, 就不要再在外部按同一个速度移动一次. 如果位置最终由游戏物理决定, 则要把物理执行后的真实位置和速度传回, 供下一轮预测使用. 需要先明确谁负责移动, 再安排两套系统交换状态.

## 3. 参数都带着物理含义

RVO2 的参数定义见[官方参数表](https://gamma-web.iacs.umd.edu/RVO2/documentation/2.0/params.html). 先统一距离和时间单位, 再调这些参数:

| 参数            | 控制什么               | 调试时看什么               |
| --------------- | ---------------------- | -------------------------- |
| radius          | 避障模型的身体半径     | 与碰撞体和导航净空是否一致 |
| maxSpeed        | 速度上限               | 期望速度是否长期要求超速   |
| neighborDist    | 搜索邻居的中心距离范围 | 危险对象是否尚未被纳入     |
| maxNeighbors    | 保留的邻居数量上限     | 高密度下是否截掉关键邻居   |
| timeHorizon     | 对其他角色的预测时间窗 | 是否过晚躲避或过度保守     |
| timeHorizonObst | 对静态障碍的预测时间窗 | 墙边是否提前受限           |
| timeStep        | 一次仿真推进的时间     | 是否与实际执行的步长一致   |

半径不是缓解堵门的万能旋钮. 把它调到比实际碰撞体小, 可能只是让算法允许游戏几何无法接受的间距. 把邻居数限制得很小也不能简单理解成无损优化.

可以用一个自设的速度上界检查邻域范围是否明显不足. 两个半径均为 0.4 的角色, 最高各以 2 单位/秒运动, 时间窗为 2 秒, 那么在匀速假设下, 窗口内可能接触的初始中心距离最多为:

$$
0.4+0.4+(2+2)\times2=8.8.
$$

若邻域只覆盖 3, 一些 2 秒内的潜在相遇还没被考虑. 这个上界只是用于理解范围与时间窗的关系, 不是通用默认值, 也不能补救邻居数量截断, 陈旧状态和错误速度上界.

## 4. 到达目标, 不是让所有圆心重合

十个有体积的士兵不可能同时站在一个点上. 玩家点击地面时, 游戏需要把这个点解释成具体任务: 排成队形, 进入附近区域, 还是轮流走到某个交互位置? 目标分配不同, 后面的停止条件也不同.

可以按需求选择:

- 编队移动: 给不同单位分配不同槽位, 避免争同一个落点.
- 集结移动: 使用容纳人群的目标区域, 接近后选择可站立位置.
- 单点交互: 只有被允许的角色靠近, 其他角色进入等待队列.

进入到达区域后, 期望速度可以归零, 但这个角色仍占据空间. 如果它停在唯一入口, 后面的人就过不去. 应安排到达后继续离开入口, 或把等候位置放在通道外.

对没有惯性的简化模型, 距离目标还剩 d 时, 让期望速度不超过 d/Δt 可以防止一步跨过目标. 真实加速度受限的角色需要提前制动; 不能在 ORCA 求解完成后再任意缩放速度, 因为缩放后的点未必仍在允许半平面内.

## 5. 窄门前, 停住可能正是避碰在起作用

两人并排通过, 最低需要的净宽至少是两人的直径之和, 实际还要考虑墙边和误差余量. 走廊只能单人通过时, 对向角色即使各有可达路线, 也不代表能同时通过.

门确实只能过一个人时, 就需要决定哪边先走, 哪边后退, 等待者站在哪里. 可以给门或窄桥安排临时通行预约, 把顺序告诉角色. 单纯增大排斥力, 并不能替他们作这个决定.

下面是建议的诊断顺序, 不是 ORCA 自带的完整死锁检测器:

| 观察到的现象 | 先检查 | 可能需要的处理 |
| 人一直朝墙走 | 全局路线与障碍版本 | 重建场或重规划通道 |
| 人能停住, 但双方谁也不过门 | 门宽, 退让空间, 通行顺序 | 排队, 预约或让一侧后退 |
| 大家挤在终点附近 | 是否共享同一个落点 | 目标区域与槽位分配 |
| 人在门口左右抖动 | 路线平局, 目标变化, 执行延迟 | 稳定选择与状态同步 |
| 只有高速时穿透 | 步长, 邻域, 实际碰撞检测 | 提前预测并检查连续运动 |

判断"长时间没进展"也不要只比较到终点的直线距离. 绕墙本来就可能先远离目标. 可以观察沿当前路线的剩余代价, 当前任务是否在等待, 以及一段时间内的真实位移, 再决定是否触发恢复策略.

## 6. 拥堵进入流场后, 还会产生反馈

如果两条路都通向目标, 单纯的最短路场可能把所有人送进同一条窄路. 给拥挤位置加代价, 是一种值得尝试的全局反馈.

但若每一帧都把瞬时密度直接写入代价, 所有人可能一起发现左路贵了, 一起转去右路, 下一帧又一起转回来. 这是路线选择与密度互相影响产生的振荡, 不一定是局部避障公式写错.

可以尝试隔几帧再更新高层路线, 平滑一段时间内的密度, 或等另一条路明显更好时才改道. 也可以让不同小组分批选路. 这些办法都需要在实际场景中比较, 本文还没有测出哪一种更好.

同样, 分离力, 队形吸引和绕障偏好最好先合成期望速度, 再交给避障求解. 在安全速度上最后叠加一股未经检查的力, 会让之前的约束失效.

## 7. 从小场景开始验, 不先堆一千个人

以下是可复现的实验清单, 本文没有声称已经实现或跑过这些人群仿真. 每次只改变一个因素, 保存相同的初始状态和随机种子.

| 场景     | 要回答的问题                | 应记录的量                   |
| -------- | --------------------------- | ---------------------------- |
| 单人绕墙 | 全局方向是否正确?           | 路线代价, 是否穿墙, 是否到达 |
| 两人迎面 | 相对速度和约束方向是否写反? | 最近间距, 新速度, 半平面残差 |
| 同向追赶 | 是否正确使用双方实际速度?   | 超车过程, 制动时机           |
| 十字交叉 | 多个约束是否同时满足?       | 冲突数量, 停顿时间           |
| 双向窄门 | 是碰撞错误还是缺少通行调度? | 通行顺序, 等待时间, 到达比例 |
| 终点集结 | 目标区域是否有足够容量?     | 停止位置, 入口占用           |
| 新建建筑 | 场缓存是否正确失效?         | 地图版本, 旧路线使用时间     |
| 初始重叠 | 退化分支是否稳定?           | 非有限数值, 分离时间         |

碰撞检查应独立于选速逻辑. 在匀速一步内, 用上一篇的最近接近公式检查整段运动, 不能只看步末有没有重叠. 两人可能已经在一大步里互相穿过去, 结束时又分开了.

运行变慢时, 先分别计时: 是构场慢, 找邻居慢, 选速度慢, 还是执行运动慢? 记录时同时写下地图大小, 单位数量与密度, 目标数量, 邻居上限和硬件. 否则一句 "支持上千单位", 很难用来判断另一张地图是否也能跑得动.

## 8. 下一步该加哪种能力

缺什么能力, 可以从现象判断. 很多人反复计算同一个远方目标, 可以考虑共享流场; 身边的人相撞, 就检查避障计算与实际执行; 双方堵在单人通道, 则需要通行顺序. 如果玩法要求每个时隙严格占据某个格子, 还得明确建模多智能体路径规划, 调整避障半径解决不了这个要求.

实现顺序可以沿着本组笔记: 先让静态地图中的单个角色正确行走, 再验证两人相遇, 接着增加多个邻居, 最后加入窄门和目标分配. 每一层的输出都能单独画出来, 才容易知道堵住时到底该改哪一层.
